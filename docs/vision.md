# Musubi ビジョン・要件定義

## ミッション

**フロントエンドとバックエンドを1つの言語で結び、人間が読みやすくAIが書きやすい、オールインワン言語を作る。**

Webアプリを作るとき、現状はTS + React + Node + 各種ビルドツールと多数の道具を組み合わせる必要がある。Musubiは「言語・UI・サーバ・ツールチェーン」を1つの一貫した体験として提供する。

## 絶対軸(譲らないもの)

| 軸 | 意味 | 検証方法 |
|---|---|---|
| FE+BE両対応 | 1言語・1リポジトリでブラウザUIとサーバの両方が書け、型を共有できる | サンプルのフルスタックアプリ(TODOアプリ等)がMusubiだけで完結する |
| 人間に読みやすい | Go的なシンプルさ。書き方が複数ない。読む人が推測しなくてよい | 仕様の小ささ(予約語・構文数を計測)、コードレビューでの理解速度 |
| AIに書きやすい | AIが一発で正しいコードを書ける確率が高い | 「白紙AI+言語カード」実験(仕様サマリだけ渡したAIにアプリを書かせる)で計測 |

## 「AIに書きやすい」の具体定義

1. **文法の一意性**: 同じことを書く方法が原則1つ(fmtで強制)。
2. **局所性**: ファイル単体を読めば意味が分かる。暗黙のグローバル・魔法のimportがない。
3. **明示性**: エラーは値(union)、副作用は見える形。隠れた例外・暗黙の型変換なし。
4. **機械可読なエラー**: コンパイルエラーは位置・原因・修正候補を構造化して出す(AIが自己修正ループを回せる)。
5. **網羅性検査**: matchの網羅性チェック(全ケースを処理し忘れていないかの検査)のように、コンパイラが「書き漏れ」を機械的に検出する。

## いいとこ取りの元ネタ(採用候補)

| 元 | 取るもの | 取らないもの |
|---|---|---|
| TypeScript | 型システムの表現力(union型・ジェネリクス・narrowing=条件分岐による型の絞り込み) | any型・型体操の複雑さ・歴史的経緯(==と===の二重の等価演算子) |
| Go | 仕様のシンプルさ、struct、明示的エラー処理の思想、標準fmt、高速コンパイル | nilの扱い、ジェネリクスの後付け感 |
| React | コンポーネント・宣言的UI・リアクティビティ(state更新で画面が自動で描き変わる仕組み) | JSライブラリであることに起因する複雑さ(hooksのルール等) |
| Rust | enum+matchの網羅性、エラー設計、ツールチェーン(cargo)の一体感 | 所有権・ライフタイム(GC言語にするので不要) |

## 非目標(Non-goals)

- ネイティブバイナリ生成・システムプログラミング(OSやゲームエンジンを書く言語ではない)
- 既存JS/TSコードとの完全互換(interopはFFI経由で明示的に行う)
- モバイルネイティブ対応(将来検討はあり得るが軸ではない)
- 実行性能の極限追求(実用十分でよい。開発体験とAI親和性を優先)

## 成功指標(遠い目標)

1. TODOアプリ級のフルスタックアプリがMusubiのみで書け、動く。
2. 白紙のAIに言語カード(仕様サマリ)を渡すと、初見で動くアプリを書ける。
3. 作者自身が新しいツールを作るときMusubiを選びたくなる。
