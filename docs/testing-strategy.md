# テスト戦略

コンパイラは「入力(ソース)→出力(JS or エラー)」の純粋な変換器なので、テストの主力は**スナップショットテスト**(正しい出力を保存しておき、出力が変わったら差分で検知する方式)になる。

## テストの4層

| 層 | 対象 | 手法 | ツール |
|---|---|---|---|
| 1. ユニット | lexer/parserの個別挙動 | 通常の`#[test]` | cargo test |
| 2. スナップショット | AST・型検査結果・生成JS・**エラーメッセージ** | 入力.msbに対する出力をゴールデンファイルとして保存し、差分が出たら意図的か確認 | `insta` クレート |
| 3. 実行E2E | 生成JSの実行結果 | .msbをコンパイル→Nodeで実行→stdout比較 | カスタムハーネス |
| 4. conformance | 仕様と実装の一致 | 仕様書の正例・負例と1:1対応するテスト群(tests/) | 自作ランナー |

## 原則

1. **新機能 = 正例スナップショット + 負例(エラーになるべきコード)をセットで追加**。負例なしの機能追加はレビューで弾く。
2. **エラーメッセージもスナップショット対象**。メッセージ品質はMusubiの主力機能(AI自己修正ループの質)なので、劣化をテストで検知する。
3. conformanceテストは仕様書の章番号でディレクトリを切る(`tests/03-expressions/`等)。仕様に書いたのにテストがない状態を作らない。
4. 型検査の負例は「エラーが出ること」だけでなく「**正しい位置・正しい種類のエラーが出ること**」まで検証する。
5. **検証(verify)とレビュー(review)を区別する**。コードを読んで良さそう、では完了にしない。生成JSを実際にNodeで実行し、受け入れ基準の挙動を確認して初めて「done」と報告する。

## 将来(実装が育ってから)

- **ファジング**: ランダム入力でコンパイラがパニックしないことを確認(cargo-fuzz)。
- **白紙AI+言語カード実験**: AIに仕様サマリだけ渡してアプリを書かせ、詰まった箇所を仕様の欠陥候補として収集する。「AIに書きやすい」の実測手段。
- 実アプリコーパス: examples/のアプリ群を常時コンパイル・実行するCI。
