# 文章スタイルガイド — ドキュメント・出力・そして言語設計へ

このガイドは3つに適用する: ①docs/以下の全文書 ②Claudeの解説・報告の文章 ③将来のMeshが出す文言(エラーメッセージ・CLI出力)の設計原則。

根拠は「公用文作成の考え方」(文化審議会建議2022)、プレインランゲージ+認知負荷の研究、エラーメッセージ可読性研究(Becker et al., CHI 2021)。

## 原則1: 読み手を起点にする

- このリポジトリの読み手は「コードは書かないが仕組みを学びたいユーザー」と「毎セッション記憶を失うAI」の2者。**どちらも前提知識を仮定できない**。
- 専門用語は排除ではなく**初出で短く説明してから使う**(例:「AST(コードのツリー表現)」)。説明済みの用語は言い換えず同じ語を使い続ける(表記ゆれは読み手の負荷)。
- 読み手が推測で補う文章を書かない。「等」「など」でごまかさず、例を1つ挙げる。

## 原則2: 認知負荷を下げる構造

- **結論を先頭に**。理由・経緯は後ろ。文書もセクションも段落もこの順(逆ピラミッド)。
- **一文一義**。1つの文には1つの内容。長い文は分割する(目安: 読点3つを超えたら疑う)。
- 1段落1トピック。3〜4文を超える段落は分ける。
- 箇条書き・表は「列挙・比較」のときだけ使い、説明は地の文で書く。箇条書きの乱用は構造の偽装になる。
- 見出しだけ拾い読みして文書の主旨がつながるようにする。

## 原則3: 明快な文

- 能動態を基本にする(「〜される」より「コンパイラが〜する」)。主語を省略して曖昧になるなら省略しない。
- 二重否定・遠回しな表現を使わない(「〜できなくはない」→「〜できる」)。
- 抽象語(「適切に」「柔軟に」「いい感じに」)で逃げない。数値・例・条件で具体化する。
- カタカナ語は定着したもののみ。和語で通じるなら和語(「アグリーメント」→「合意」)。

## 原則4: Meshの文言設計への適用(エラーメッセージ等)

エラーメッセージ可読性研究(Becker et al.)は、可読性を決める3因子として**長さ・トーン・専門用語**を特定した。RustとElmの実践も踏まえ、Meshの文言は以下を仕様とする:

1. **短く**: 本文は1〜2文。詳細は `mesh explain E0301` のように段階的に開示する(Rustの `--explain` 方式)。
2. **責めないトーン**: "invalid" "bad" のような否定語・ユーザーを責める表現を避ける。「何が起きたか→どう直せるか」を淡々と示す(Elm方式)。
3. **平易な言葉**: 普通のプログラマが小さい画面で読んで分かる語彙で書く。内部実装の用語(unification等)を漏らさない。
4. **位置+原因+修正候補**の3点セット。該当コードを示し、可能なら修正案を提示する。
5. 人間向けの文言と機械向けの構造化出力(JSON)は同じソースから生成し、内容を一致させる。
