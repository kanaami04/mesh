# プログラミング言語はどう作られるか — Musubi開発のための基礎教材

Musubiを作る上で「ここまで分かっていれば議論に参加できる」ラインを目指した教材。

## 1. 言語処理系の全体像 — どの言語も中身は同じパイプライン

どんな言語(Python, Go, TS, Rust...)も、処理系の中身はほぼ同じ段階を踏む:

```
ソースコード (文字列)
  │
  ▼ ① 字句解析 (Lexer / Tokenizer)
トークン列          "let x = 1 + 2" → [let] [x] [=] [1] [+] [2]
  │
  ▼ ② 構文解析 (Parser)
AST (抽象構文木)     let文(x, 加算(1, 2)) というツリー構造
  │
  ▼ ③ 意味解析 (Semantic Analysis)
検査済みAST         名前解決(このxはどこで宣言された?)+ 型検査(1+2はint?)
  │
  ▼ ④ (任意) 中間表現 IR + 最適化
  │
  ▼ ⑤ コード生成 (Codegen)
出力                機械語 / バイトコード / 別言語のソース(JS等)
```

- **①字句解析**: 文字の並びを意味の最小単位「トークン」に切る。正規表現的な単純作業。
- **②構文解析**: トークン列を文法規則に従ってツリー(AST)にする。`1 + 2 * 3` が「1 + (2*3)」になるのは、パーサが演算子の優先順位を知っているから。ここで文法エラー(「`)`が足りません」)が出る。
- **③意味解析**: ツリーの「意味」を検査する。未定義変数の使用、型の不一致などはここ。**Musubiの価値(union型、網羅性検査、良いエラー)はほぼこの層で作る。**
- **⑤コード生成**: MusubiはここでJavaScriptのソースコードを出す(=トランスパイル)。

**重要な感覚**: ①②は確立された技術で難所ではない。言語の個性と品質は③(型システム・エラーメッセージ)と、言語設計そのものに宿る。

## 2. 実行方式の分類 — 「コンパイル方式」の全体地図

| 方式 | 仕組み | 代表例 | 特徴 |
|---|---|---|---|
| ツリーウォーク・インタプリタ | ASTを直接たどりながら実行 | 初期Ruby、多くの自作言語 | 最も簡単。遅い。学習用に最適 |
| バイトコードVM | 独自の中間命令列に変換し、専用VM(ソフトウェアのCPU)が実行 | Python, Java(JVM), Erlang(BEAM) | 移植性が高い。VMも自作対象になる |
| JITコンパイル | 実行中に頻出部分だけ機械語へ変換 | V8(JS), JVM | 高速だが実装は最高難度 |
| AOTネイティブコンパイル | 事前に機械語まで変換 | Go, Rust, C | 高速・単一バイナリ。機械語生成はLLVM等に任せるのが普通 |
| **トランスパイル** | **別の高級言語のソースへ変換** | **TS→JS, Gleam→JS/Erlang, Kotlin→JS** | **実行は既存処理系にタダ乗り。Musubiはこれ** |

### Musubiがトランスパイル方式(JSターゲット)を選んだ理由

1. **FE+BE両対応が最短で成立**: JSはブラウザとNode/Bunの両方で動く唯一のランタイム。
2. **GC(メモリ管理)を作らなくていい**: JSエンジンのGCにタダ乗りできる。自前でGCを書くのは大仕事(§4)。
3. **エコシステムにタダ乗り**: npmのライブラリをFFI経由で呼べる。V8のJIT最適化も享受できる。
4. **デバッグ**: ソースマップ(生成JSの行↔Musubiソースの行の対応表)を出せば、ブラウザのDevToolsでMusubiのソースを見ながらデバッグできる。TSと同じ仕組み。

## 3. WASMとは何か(そしてなぜ今回は選ばなかったか)

WebAssembly(WASM)は「ブラウザでも動く、特定言語に依存しないバイナリ命令形式」。C/Rust/MoonBitなどがコンパイル先にしている。

- **強み**: 実行が速い、バイナリが小さい、言語を選ばない。ブラウザ外でも動く(WASI=サーバ側WASM標準)。
- **弱点(FE言語にとって致命的な点)**: **WASMからDOM(HTML要素)を直接触れない**。ボタンを1個描くにもJSのグルーコード(橋渡し層)を経由する必要があり、FEフレームワークを作る難度が跳ね上がる。
- **wasm-gc**: 従来WASMはGCがなくRustのようなGC不要言語しか快適に使えなかったが、wasm-gc提案でホスト(ブラウザ)のGCを借りられるようになった。MoonBitはこれを活用している。
- **Musubiの立場**: 初期はJSターゲットに集中。ただしAST→出力の間を疎結合に設計しておき、将来「wasmバックエンド追加」の道を残す(MoonBitもGleamも複数バックエンド構成)。

## 4. ランタイムとGC — 「言語を作る」に含まれる見えない仕事

コンパイラ本体の他に、言語には「ランタイム」(実行時に必要な支援コード)が要る:

- **GC(ガベージコレクタ)**: 使い終わったメモリの自動回収。方式は参照カウント(Swift)、マーク&スイープ(JS, Go)など。自作すると数千〜数万行級の難所。**JSターゲットなら丸ごと不要**(最大の省力ポイント)。
- **値の表現**: Musubiの`string`や`list`をJSの何に対応させるか(JS string / Array に直接マップするのが基本)。
- **組み込み関数**: print、文字列操作などの標準ライブラリの土台。JSターゲットでは「小さなJSヘルパーライブラリ」として同梱する。

## 5. 型システム — Musubiの主戦場

- **静的型付け**: コンパイル時に型を検査(TS, Go)。Musubiは静的。
- **名前的 vs 構造的**: Goは「型名が同じなら同じ型」(名前的)、TSは「形が同じなら同じ型」(構造的)。構造的は柔軟だが「意図しない型の一致」が起きやすい。Musubiでどちらを採るかはPhase 1の主要議題。
- **型推論**: 全部書かなくても型が決まる仕組み。
  - 完全推論(Hindley-Milner。OCaml/Haskell系。注釈ほぼ不要だが、エラーが遠くで爆発しがち)
  - **局所推論(TS/Go/Rust流。関数の引数・戻り値は書く、ローカル変数は省略可)** ← 読みやすさ・AI親和性の観点でMusubi向き。関数シグネチャ(引数と戻り値の型情報)が常に明示されると、AIはその関数の中だけ読んでコードを書ける。
- **union型と網羅性検査**: `T | none` のような「どちらか」型と、matchで全ケース処理を強制する検査。null安全と明示的エラー処理を両立する有力候補(Phase 1で議論)。

## 6. 言語は「コンパイラ」だけでは完成しない — ツールチェーンの全体像

現代の言語が使われるために必要なもの一式:

| 部品 | 役割 | Musubiでの計画 |
|---|---|---|
| コンパイラ | .msb → .js | Rustで自作(本体) |
| CLI | build/run/dev/test... | cargo風の一体型CLI `musubi` |
| フォーマッタ | 唯一の整形(gofmt思想) | 自作。文法の一意性の実行部隊 |
| LSP | エディタ補完・エラー表示 | 自作(tower-lspクレート)。Language Server Protocolという標準に乗るとVSCode等で一斉に動く |
| パッケージマネージャ | 依存管理 | 初期はnpm相乗りを検討 |
| テストランナー | 言語組み込みテスト | `musubi test` を言語仕様に含める |
| ソースマップ | デバッグ対応 | JS生成時に出力 |

## 7. 自前でどこまで作るか — Rustエコシステムの地図

| 層 | 自作? | 使えるRustクレート |
|---|---|---|
| 字句解析 | 自作(簡単)or logos | `logos`(高速lexer生成) |
| 構文解析 | **手書き再帰下降を推奨** | パーサジェネレータ(chumsky等)もあるが、**良いエラーメッセージ(=AI自己修正の質)は手書きが圧倒的に有利**。Rust/Go/TS本家もすべて手書き |
| 型検査 | 完全自作(言語の個性そのもの) | — |
| JS生成 | 自作(文字列組み立て+ソースマップ) | `sourcemap`クレート等 |
| LSP | プロトコル部分はクレート | `tower-lsp` |
| テスト | スナップショット | `insta` |

**結論**: 難所のGC・機械語生成・JITをすべて回避できるのがJSトランスパイル方式。字句〜JS生成までを全部自作しても現実的な規模で、しかも言語処理系の学びは一通り体験できる。

## 8. 用語ミニ辞典

- **AST**: 抽象構文木。コードのツリー表現。コンパイラ内の共通言語。
- **IR**: 中間表現。ASTと出力の間に置く中立フォーマット。複数バックエンド(JS/wasm)を見据えるときの絶縁層。
- **セルフホスト**: 言語自身でそのコンパイラを書き直すこと(GoコンパイラはGo製)。遠い夢としてはMusubiコンパイラをMusubiで書ける。
- **ボトムアップ/トップダウン構文解析**: パーサの2大方式。手書きするのはトップダウン(再帰下降)。
- **ドッグフーディング**: 自分の言語で実物を作って穴を見つけること。
