# ADR-0034: 式の詳細(matchは型パターンのみ・範囲式はforヘッダ限定・narrowingは変数のみ)

- **Status**: accepted
- **Date**: 2026-08-14
- **決定者**: ユーザー + Claude(仕様3章の執筆時に確定)

## Context

仕様3章の執筆で式レベルの範囲決定が3つ必要になった。

## Decision

1. **matchのパターンはv1では「型パターン+束縛+`_`」のみ**(`User u =>` / `none =>` / `_ =>`)。リテラルパターン(`200 =>`)は置かず、値の分岐はif/else ifで書く。需要が実証されたら後から追加できる(逆は破壊的変更)。
2. **範囲式 `0..n` はforヘッダ専用の構文**であり、第一級の式・Range型ではない(設計監査#12の決着)。
3. **narrowing(`is`)の対象はローカル変数とパラメータのみ**(v1)。フィールドパス(`u.addr is ...`)は対象外とし、変数に取り出してから絞り込む。mutな変数への再代入は絞り込みを無効化する。

## 検討した代替案と捨てた理由

- **リテラルパターン**: Go switch風で便利だが、網羅性の意味論が複雑化し「ifとmatchの使い分け」という新しい判断ポイントを生む。
- **第一級Range型**: 型・イテレータ概念が増える。用途はforでほぼ全て。
- **フィールドパスnarrowing**: 前実装に実装例があるが、無効化条件(どの代入がパスを壊すか)の追跡が複雑で、v1のエラーメッセージ品質を優先。

## 既存ADRとの相互作用

- ADR-0005(narrowing・網羅性): 本ADRはその適用範囲のv1限定。
- ADR-0019(forの3形): 範囲式の位置づけを確定(forヘッダの一部)。
- ADR-0008(シャドーイング禁止): matchの束縛名にも適用される(仕様3章で明文化)。

## Consequences

- 仕様3章に規範として明文化する。リテラルパターン要求時のエラーはifへの誘導メッセージを持つ。
