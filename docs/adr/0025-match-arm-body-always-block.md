# ADR-0025: matchの腕は `パターン => { ... }`(本体は常にブロック)

- **Status**: accepted(ADR-0016 を supersede。`=>` の採用は本ADRに引き継ぐ)
- **Date**: 2026-08-14
- **決定者**: ユーザー + Claude

## Context

ADR-0016は `=>` 区切り+「短い腕は式1つ、複数文はブロック」の2形を認めていた。ユーザーのレビューで2つの問題が指摘された: ①複雑な腕と単純な腕でブロックの有無が混ざり、腕ごとに形が非対称になる(見栄え)。②式形の腕は行末でしか終端が分からず、AIが「ブロックにするか否か」を毎回判断する必要がある(判断ポイント=間違いポイント)。

## Decision

腕の本体は**常にブロック**とする。

```
match res {
  Data d => {
    let user = json.decode<User>(d.body)?
    save(user)
    "保存しました"
  }
  none  => { "データなし" }
  Err e => { "失敗: ${e.message}" }
}
```

- 区切りは `=>`(ADR-0016から引き継ぎ。パターンと本体の視覚的区切り)。
- 終端は常に `}`。ブロックの最後の式がその腕の値(if式と同じ規則)。
- 短い腕は1行形 `none => { "データなし" }` で書ける(fmtが整形)。

これで「**制御構造の本体は常に波括弧ブロック、ブロックの最後の式が値**」という規則がif・matchに共通で1本になる。

## 検討した代替案と捨てた理由

- **2形維持(ADR-0016)**: 上記①②の問題。
- **式形+末尾カンマ(Rust風)**: 終端の目印にはなるが、廃止したセミコロン系の区切り記号が出戻る。

## Assumptions

- (特になし。見た目はJS/TSのアロー関数 `x => { ... }` と同型で、AIの馴染みも深い)

## Consequences

- パーサは「`=>` の次は必ず `{`」を期待でき、エラーメッセージも一意に書ける(「matchの腕には `{ ... }` が必要です」)。
- 全腕が同じ形になるため、fmtの整形規則(`=>` と `{` の位置揃え)が単純になる。
