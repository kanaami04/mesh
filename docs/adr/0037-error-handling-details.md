# ADR-0037: エラー処理の詳細(error値の構造・error type不採用・cause連鎖)

- **Status**: accepted
- **Date**: 2026-08-14
- **決定者**: ユーザー + Claude(仕様6章の執筆時に確定。ADR-0005の詳細化)

## Context

仕様6章の執筆で、ADR-0005が「詳細はラウンド2以降」とした3点を確定する必要があった: 組み込みerror値の構造、構造化エラーの宣言形、`? "文脈"` の内部表現(spec/overviewの検討メモ「文字列畳み込みではなくcause連鎖で保持」の実装)。

## Decision

1. **組み込み `error` 値の構造**: `message: string` と `cause: error | none` の2フィールド(読み取りのみ)。生成は**生成式** `error(message)`(専用の構文形。`error` は予約語のため関数値としては参照できない)。
2. **構造化エラーの宣言は `error struct` のみ**。`error type` は置かない — type別名は透過(T-5)なので、error structのunionに通常の `type` で名前を付ければ足り、伝播対象性はメンバーごとに決まる(マーカーはstruct側だけで一意)。
3. **`? "文脈"` のcause連鎖**: 昇格で生成される組み込みerrorは `message = 文脈`、`cause = 元の失敗を表す組み込みerror値`(元が組み込みerrorならそのまま、error structなら**型名とフィールドを表示文字列に展開したmessageを持つ通常のerror値**に変換、noneなら `none`)。ログ・表示でフィールドの情報が失われないことをmessage展開で保証する(errorの2フィールド定義=決定1と完全に整合し、特殊な実行時表現を持たない)。**cause連鎖から構造化エラーを型付きで取り出す手段はv1に無い**(型付きで扱いたい場合は `? "文脈"` を使わず素の `?` でメンバーを戻り値unionに明記して伝播する)。v1ではcauseを手動で設定する手段も無い(将来 `error(message, cause)` の拡張余地)。

## 検討した代替案と捨てた理由

- **文字列への畳み込み**(前実装方式): 構造化エラーのフィールドが文脈を付けた瞬間に消える(検討メモで却下済み)。
- **error type宣言の採用**: 前実装には存在したが、Meshでは無名unionメンバーが無く(2章)、型別名が透過なため冗長。宣言種を1つ減らせる。
- **causeの型を「全失敗のunion」にする**: 静的に列挙不能。型付き回収は素の `?` が担う、という役割分担が明快。

## 既存ADRとの相互作用

- ADR-0005: 規則4(文脈付き伝播)・規則7(構造化エラー)の詳細化。「宣言側の明示マーカー」の原則は維持(マーカーはerror structに一本化)。
- ADR-0027(panic境界): panicとerror値の2系統分離は不変。panicの一覧と境界の挙動は仕様6章に集約。同章H-7により、境界回復の対象は「MeshPanic **および境界で事後分類された資源枯渇のエンジン例外**」に精密化される(0027の「MeshPanicのみ」の文言を本ADRで更新)。
- 2章T-21・T-9: 「error struct/error type」の表記を「error struct」へ整理(本ADRによるdrift修正)。

## Consequences

- 仕様6章に規範として明文化する。2章・3章の「error type」参照を修正する。
- 実行時のerror表現はmessage/cause/元値を持つタグ付きオブジェクト(A-7の設計対象)。
