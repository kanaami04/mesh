# ADR-0049: 先送りは申し送り台帳に集めてトリガーで撃つ、括弧の種類写像は BracketKind に統一する

- **Status**: accepted
- **Date**: 2026-08-20
- **決定者**: ユーザー + Claude

## Context(何を決める必要があったか)

### 1. 先送りした決定が読まれないまま放置される

ADR-0047・0048 で「いまは決めない」と判断した事項を roadmap に散文で書いてきた。しかしこの置き方は機能していない。2026-08-20 に実測したところ、roadmap の該当行は **1,976文字**あり、「パーサ着手前のリファクタ候補」は**その1,166文字目**にあった。画面に出ない位置である。

**取りこぼしが実際に起きていた。** BOM(U+FEFF)の扱いは roadmap が「実ファイルを読ませる前=CLI整備までに決定する」と期限を定めていたが、ADR-0048 で読み込み層(`src/main.rs`)に手を入れた際に判断されないまま通過した。期限は満たされなくなっている。

GitHub issue に出す案も検討したが、**読みに行く機構が無いため放置される**というのがユーザーの見立てで、これは妥当である。問題は置き場所ではなく、**読まれるトリガーが無いこと**だった。

一方、同じ構造の問題をこのリポジトリは既に解いている。ASSUMPTIONS.md(前提台帳)は `検証予定` 列で「いつ読むか」を持ち、`drift-check` スキルがフェーズ完了時に全量を見直す。**台帳と読む機構がセットになっている**から機能している。先送り事項にはこの対がなかった。

### 2. 括弧の種類写像が二重に定義されている

ADR-0047 決定1 で `lex` と `scan_interpolation` の照合**方式**は揃えたが、実装の共通化は範囲外とした。`lex` は `Vec<BracketKind>`、`scan_interpolation` は `Vec<TokenKind>`(期待する閉じ括弧を積む)で、`LParen → RParen` の写像を別々に持っている。

さらに前提 A-26 により、**パーサも括弧の不均衡を報告する責務を負う**。このままだとパーサが3つ目の写像を書くことになる。

## Decision(何に決めたか)

### 1. 申し送り台帳 `docs/adr/DEFERRED.md` を作り、トリガーで撃つ

先送りした決定・作業は台帳に集める。ASSUMPTIONS.md の姉妹として同じ表形式にし、`トリガー` 列に「いつ読むか」を機械可読な書式で書く。

| 書式 | 意味 | 誰が撃つか |
|---|---|---|
| `file:<パス>` | そのファイルを触ったとき | **PreToolUseフック**(機械) |
| `phase:<番号>` | そのフェーズに**入る直前**(= 前のフェーズの完了時) | drift-check |

**`file:` を優先する。** 人が発火させる機構は、案A(GitHub issue)を棄却したのと同じ弱さを持つ——フェーズの**完了**は roadmap を更新する明示イベントがあるが、**開始**は誰も宣言しない。代表ファイルが決められるものは `file:` に落とす(impl-reviewの助言)。D-4 は Phase 9 の実験記録 `docs/research/phase9-ai-card-experiment.md` を代表に据えた。`phase:`/`layer:` は代表ファイルが定まらないもの(D-5・D-6 のエラーメッセージ層など)に限る。
| `layer:<名前>` | その層の実装サイクルで | drift-check |

`file:` のトリガーは `.claude/hooks/deferred-check.sh` が撃つ。Edit/Write の直前に該当行を `additionalContext` で提示する。**`permissionDecision` は返さない**——`"allow"` は許可プロンプトを飛ばすため、「着手前に人が判断すべき」と印を付けたファイルに限って許可判断を奪うことになる(impl-reviewで検出)。決定を省けば通常の許可フローが働き、情報だけが届く。同じ(セッション, ID)の組では1回だけ出す——毎回出すと雑音になる。

**行は消さない**(歴史を消さない=ADR運用ルールと同じ)。対応が済んだら状態欄を `解決(理由)` に書き換える。フックは状態欄が「解決」で始まる行だけを黙らせる。

### 2. 括弧の種類写像を `BracketKind` に統一する

`scan_interpolation` の `Vec<TokenKind>` を `Vec<BracketKind>` に替え、`from_open`/`from_close` を使う。写像の定義を1箇所にする。

**ループ本体の一本化はしない。**不一致時の方針が違うため原理的にできない——`lex` は黙って通す(不均衡はパーサの担当)が、`scan_interpolation` はその場で E0109 を報告し、空スタックの `}` は補間の終端になる。共通化できるのは写像だけである。

**専用構造体(`BracketStack` 等)への抽出は先送りする。**パーサが何を必要とするかは A-26 の検証(パーサ実装時)で初めて分かるため、いま設計するとパーサの実態に合わない部品になる危険がある。台帳の **D-1** として登録し、`file:src/parser.rs` をトリガーにした。

## 検討した代替案と捨てた理由

**案A(1について): GitHub issue で管理する。** リポジトリ外の道具に出すと、読みに行く機構が無いまま放置される。issue を定期的に読む運用は人の規律に依存し、このプロジェクトが機械的強制(Stopフック)を選んできた方針と合わない。棄却。

**案B(1について): roadmap を読める形に整理するだけ。** 2,000文字の行を分割すれば見えるようにはなる。しかし**トリガーは人の目に依存したまま**で、BOM の取りこぼしと同じことが再発する。棄却(ただし roadmap の可読性改善自体は別途行う価値がある)。

**案C(2について): 共通化しない。** 得られるのが3行の削減なら見合わないという判断もありうる。しかし本質は行数でなく**写像の単一定義**で、パーサが3度目の写像を書く前に統一する価値がある。ADR-0047 で直したのと同じ型の事故(一方だけ直して他方が取り残される)の再発面を残すことになる。棄却。

**案D(2について): いま専用構造体まで作る。** パーサでの再利用を最大化できるが、パーサの要求が未確定のまま設計することになる。D-1 として先送りし、トリガーで撃つほうが安全。棄却。

## Assumptions(この決定が依存している前提)

- **A-29**: PreToolUseフックの `additionalContext` が、`permissionDecision` を返さなくてもモデルへ情報を届け、通常の許可フローを妨げない(2026-08-20に公式ドキュメントで確認し、実測でも検証済み。当初は `"allow"` を返しており許可判断を奪っていた——前提の文言と実装がずれていた)
- **A-30**: 先送り事項のトリガーは、着手ファイルかフェーズ/層のいずれかで表現できる(表現できないものが出たら書式を増やす)

## 既存ADRとの相互作用

- **ADR-0045(レビューゲートのセッション別分離)との相互作用**: 通知済み記録を `.claude/state/deferred-shown-<session_id>` に持つ設計は、ADR-0045 と同じ「セッション別の状態」の形に揃えた。作業ツリーごとに独立するため、並行セッションでも互いの通知を消さない。
- **ADR-0047(閉じ括弧の同種対応)との相互作用**: 決定1の「二重実装の解消は範囲外」を、本ADRで**写像に限って**実施する。スタック操作の共通化は D-1 として引き続き先送り。
- **ASSUMPTIONS.md との役割分担**: 前提台帳は「**未検証の前提**」(崩れるかもしれない)、申し送り台帳は「**先送りした決定・作業**」(いつか判断する)。混ぜない。

## Consequences(この決定の帰結・影響)

- **利点**: 先送りの書き場所が決まり、漏れなくなる。着手の瞬間に機械が提示するため、BOM のような取りこぼしが起きない。括弧の写像が単一定義になり、パーサが3つ目を書く事態を防げる。
- **コスト**: フックが1つ増える(Edit/Write のたびに走るため軽量に保つ)。台帳の手入れが要る——対応したら状態を更新しないと、解決済みの行が提示され続ける。
- **既知の限界**: `file:` トリガーは Edit/Write を経由する変更でしか撃たない(シェルでファイルを作った場合は撃たない)。`phase:`/`layer:` のトリガーは drift-check 頼りで、機械的な強制はない。
- **移行時の一度きりの作業**: roadmap に散在していた先送り6件を台帳へ移し、roadmap 側は台帳への参照に置き換えた(初回のコミットでは D-1 しか移せておらず二重管理が残っていた。impl-reviewで検出し是正)。うち1件(D-3・BOM)は**期限超過**の状態で登録した。
