# ADR-0042: 補間のトークン表現は入れ子方式(Strトークンが区分列を内包する)

- **Status**: accepted
- **Date**: 2026-08-15
- **決定者**: ユーザー + Claude

## Context(何を決める必要があったか)

仕様L-17は補間 `${式}` の中身を「通常の字句モードで再帰的にトークン化する」と定めるが、その結果を**どういう形でパーサに渡すか**(トークン列の表現)は実装の設計判断として残っていた。パーサのインターフェースを決める選択であり、後から変えると字句・構文の両方に波及するため、補間実装の着手前にADR化する。

## Decision(何に決めたか)

**入れ子方式**を採用する。文字列リテラル全体は従来どおり**1個のStrトークン**であり、補間を含む場合は中身の区分列(セグメント)を内包する:

- セグメントは「テキスト片」または「補間(再帰トークン化されたトークン列)」の並び。
- Strトークンのtextは従来どおり**クォート込みの生の字面**、spanは文字列全体。`text == source[span]` の不変条件を維持する。
- 内側のトークン(補間内の式のトークン)のspanも**ソース全体に対する絶対バイトオフセット**とする(エラー報告が常に元ファイルの位置を指すため)。

## 検討した代替案と捨てた理由

- **A: フラット分割方式**(StrStart/InterpStart/InterpEnd/StrEnd等の部品トークンを主ストリームに直接並べる。JSエンジン・Swiftの系譜): 主ストリームに文字列の破片が混ざるため、L-20(行末トークン判定)・L-21/ADR-0031(括弧深度スタック)・将来の終端挿入が「文字列の内側かどうか」を常に意識する必要が生じる。補間の複雑さが文字列の外の世界に漏れるため不採用。
- **C: パーサで再字句解析**(lexerは生のStrのまま、パーサが中身を再度lexする): 実装は最も楽だが、L-17を字句の章に置いた仕様の趣旨(E0115・E0109の報告責務が字句側)から外れ、同じ文字列を2回走査する。エラー位置の計算も二重管理になるため不採用。

## Assumptions(この決定が依存している前提)

- A-19: 入れ子セグメントと絶対オフセットspanで、パーサの再帰下降(補間内の式パース)とエラー報告が素直に実装できる(ASSUMPTIONS.md参照)。

## 既存ADRとの相互作用(2026-08-14監査の教訓により必須)

- **ADR-0031(括弧深度スタック)**: 主ストリームが従来と同形のため、深度スタックは文字列の中身を一切知らなくてよい。補間内の括弧対応はStr内部の再帰トークン化が閉じて扱う(L-17の「トークン列上で数える」)。
- **ADR-0010(終端挿入)**: 文字列は1トークンのままなので、行末トークン判定に影響しない(L-17(a)により補間を含む文字列は物理1行に収まる)。
- **token()の不変条件(text==source[span])**: 外側Strで維持。セグメントのspanも絶対オフセットなので `source[span]` 切り出しが全レベルで成立する。
- **ADR-0041(CRLF)**: 正しく閉じた補間内に改行は現れない(L-17(a))。ただし**エラー経路では相互作用がある**: 補間の内側の単独CRはE0117でなくE0109に統一する(L-18注2。2026-08-15、実装時のimpl-reviewで検出し追記)。

## Consequences(この決定の帰結・影響)

- Token型が再帰的になる(Strのみセグメント列を持つ。具体的なRust表現は実装のRedフェーズで決定し、既存テストの機械的更新を許容する)。
- スナップショットの出力が文字列で入れ子になる(補間を含む場合)。
- E0109(L-18)・E0115(L-17(b))は字句解析器が報告する。E0109×E0112の優先順位は補間サイクルの宿題(roadmap記載)としてこのADRの範囲外。
- 仕様の変更は不要(L-17は挙動のみを定めており、表現は実装判断の範囲)。
