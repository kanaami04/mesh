# ADR-0046: 実装は子セッションへ委譲し、レビューは司令セッションが持つ

- **Status**: accepted
- **Date**: 2026-08-18
- **決定者**: ユーザー + Claude

## Context(何を決める必要があったか)

コスト配分のため、実装をGLM(z.ai経由)に任せ、設計判断とレビューをClaudeが担う分担を検討した。その前提として、**GLMセッションでサブエージェントのモデル指定が効くか**を実測した。

結果は否だった。2026-08-18、GLMセッション(`9add0ce3`)のトランスクリプトを全数調査した。

| 指定した model | 実際に応答したモデル | 件数 |
|---|---|---|
| `opus` | `glm-4.7` | 13 |
| `sonnet` | `glm-4.7` | 5 |

`glm-4.7` は同セッションの `ANTHROPIC_SMALL_FAST_MODEL` の値である。一方、**セッション本体は `glm-5.3` で応答していた**(485メッセージ)。つまりサブエージェントだけが1段下の最小モデルへ落ちている。

転落した13件には `impl-review` の2観点、`doc-review` の検査1、TDDのGreen(非自明な実装)が含まれる。CLAUDE.mdは「迷ったら `opus`(安いモデルで失敗して再実行する方が高くつく)」と定めているが、その逆が起きていた。

原因は、`opus` / `sonnet` がAnthropicのモデル別名であり z.ai 側に存在しないため、解決に失敗して `ANTHROPIC_SMALL_FAST_MODEL` へフォールバックすることと考えられる。**エラーにならず静かに落ちる**ため、トランスクリプトを見ない限り検知できない。

計測方法は再現可能である。`~/.claude/projects/<project>/<session>/subagents/agent-*.meta.json` に指定したmodel、同名の `.jsonl` の assistant メッセージに実際に応答したmodelが記録される。

## Decision(何に決めたか)

**委譲の単位をサブエージェントからセッションに変える。**

- **司令(Claudeセッション)**: テストリストの作成、Redの失敗理由の確認、Refactor判断、レビュー(impl-review・doc-review・spec-review)、ADR起票、PR作成。プロダクトコードは書かない。
- **子(GLMセッション)**: テスト実装(Red)とプロダクトコード実装(Green)。**サブエージェントを使わない。レビュースキルを実行しない。**

TDDのRed/Green分離は、サブエージェントではなく**別セッション**で作る。Red子とGreen子は同じworktreeを順に使い、同時には走らせない(1作業ツリー = 1ブランチのため)。

手順は `orchestrate` スキル、子への定型指示は `.claude/skills/orchestrate/CHILD.md` に置く。

### 追補(2026-08-18・初回運用後)

**委譲の範囲を「実装」から「判断を伴わない作業すべて」へ広げる。** 初回運用(PR #31)で `glm-5.3` がRed・Greenとも完走し、期待値を仕様から導出できることを確認した。実装だけに絞るとGLMの枠が余るため、次も子へ出す: **仕様章の執筆**(spec-writeの下書き。根拠ADRは司令が確定済みのもの)、**調査・実測・検証スクリプト**、**drift-checkの全量検査**。

境界は変わらない——**サブエージェント委譲が要る作業と、設計判断は司令が持つ**。子に出してはいけないものは、レビュー3種(impl/doc/spec)・ADRの起票・仕様の決定・PR作成。

**`spec-write` との組み合わせの穴(doc-reviewで検出)**: `spec-write` は締めに `spec-review` の実行を義務づけているが、子はレビューを禁じられている。子が `spec-write` をそのまま読むと矛盾するため、**両側に例外を明記した**——子は執筆までを行い、`spec-review` は司令が `opus` で回す。

## 検討した代替案と捨てた理由

**案A: スキル側でモデル名を切り替える。** セッションのプロバイダを見て `opus` / `glm-5.3` を出し分ける。GLMセッションでも上位モデルへ委譲できるが、スキル6本の改訂が要り、プロバイダ判定という新しい分岐を全スキルに持ち込む。さらに**レビューの独立性の問題が残る**——実装したセッションが自分の実装をレビューする構図は変わらない。棄却。

**案B: GLMの利用をやめる。** 最も単純だが、コスト面の選択肢が消える。実測ではセッション本体の `glm-5.3` は実装を完走できており、能力不足の証拠は無い。棄却。

**案C: サブエージェントのまま使い、レビューだけClaudeで回す。** 実装(Green)がglm-4.7で行われる状態が残る。非自明な実装を最小モデルに任せる理由が無い。棄却。

## Assumptions(この決定が依存している前提)

- **検証済み**: GLMセッションのサブエージェントは `ANTHROPIC_SMALL_FAST_MODEL` へ落ちる(2026-08-18、18/18件で確認)
- **検証済み**: GLMセッション本体は `ANTHROPIC_MODEL` で応答する(485メッセージで確認)
- **未検証(A-24)**: z.ai側のモデル別名の解決挙動は今後も同じとは限らない。仕様として公開されたものではなく、実測から推定した挙動である
- **未検証(A-25)**: `glm-5.3` が本プロジェクトの実装タスクで十分な品質を出す。字句解析器の実装は完走しているが、レビューがglm-4.7で行われていたため品質の裏付けが弱い

## 既存ADRとの相互作用

- **ADR-0045(レビューゲートのセッション別分離)との相互作用**: 本ADRで子セッションが増えるため、レビューゲートのセッション分離が前提として効いてくる。子が編集した `.md` は子のStopフックが検知し、司令の記録には混ざらない。
  - **組み合わせの穴(doc-reviewで検出)**: 子が `src/` をコミットすると、子のStopフックが「impl-reviewを実行せよ」とブロックする。しかし本ADRは子にレビューを禁じている。ADR-0045の一発通知方式により作業は止まらない(同じコミットで1セッション1回のみ)ので、**子はこの通知を無視して完了報告に含め、レビューと台帳への追記は司令が行う**。
  - 台帳 `.claude/state/impl-reviewed-commits` は作業ツリーごとに独立するため、司令は**子のworktree側**へ追記する。司令の作業ツリーへ書いても子のフックには効かない。
- **CLAUDE.md「モデルの使い分け」との相互作用**: 「サブエージェントには `opus`/`sonnet` を常に明示指定する」規約は**Claudeセッションでのみ成立する**。GLMセッションでは無効になるため、GLM子ではサブエージェント自体を禁止する形で整合させた。
- **`tdd` スキルとの相互作用**: tddのRed/Green分離(サブエージェント粒度)と、本ADRの分離(セッション粒度)は目的が同じで粒度が違う。実装を外へ出さないときはtddをそのまま使う。

## Consequences(この決定の帰結・影響)

- **利点**: 実装が `glm-5.3` で行われ、レビューが `opus` で行われる。実装者とレビュアーが別セッションになるため、レビューの独立性も構造的に担保される。
- **コスト**: セッション数が増え、往復の管理が要る。Red子とGreen子を順に立てるため、1サイクルの手数が増える。
- **前提の脆さ**: z.ai側の挙動が変われば前提が崩れる。`.meta.json` と `.jsonl` の突き合わせで定期的に再検査する。
- **既存成果物への影響**: PR #25・#26・#28 のレビューは実体がglm-4.7だった。字句解析器の再レビューを別途行う。
