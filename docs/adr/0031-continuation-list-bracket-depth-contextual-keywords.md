# ADR-0031: 継続トークンの確定一覧・括弧深度方式・UI語の文脈キーワード化

- **Status**: accepted
- **Date**: 2026-08-14
- **決定者**: ユーザー + Claude(仕様1章の敵対的レビューで検出した3つの穴の決着)

## Context

仕様1章の執筆時レビューで、行継続規則(ADR-0026)に3つの穴が見つかった: ①括弧内の改行の扱いが未定義で、トレーリングカンマ無しの複数行呼び出し(JS/TSで最も普通の書き方)が壊れる。②キーワード演算子(`or`/`is`)と `.`/`..`/複合代入の継続可否が未定義。③UI予約語(`state` 等)を完全予約にすると `let state = ...` が全コードで書けない実用コスト。

## Decision

1. **括弧深度方式**: `(` と `[` の内側では改行は文を終端しない(Python/Rust/Swift/JSと同挙動)。ただしその内側でも `{ ... }` ブロックに入ったら終端規則が復活する(引数中の無名関数の本体のため。深度は `{` で退避し `}` で復元するスタック構造)。複数行structリテラルは各フィールドの行末カンマで継続する(最終フィールドにもカンマ必須。fmtが自動補完)。
2. **継続トークンの確定一覧**(ADR-0026の「二項演算子」を具体化+拡張): 記号二項演算子・キーワード演算子 `or` `is` `in`・複合代入 `+= -= *= /= %=`・`.`・`..`・カンマ・開き括弧・`=`・`=>`。確定一覧は仕様1章 L-20 が正。
3. **`component` / `state` / `view` は文脈キーワード**: `component` 宣言の文法内でのみ予約し、通常コードでは識別子として使える(Swift/C#で実証済みの手法)。`none` / `error` / `or` / `is` は完全予約を維持し、`or error =>` には専用の誘導メッセージを出す。

## 検討した代替案と捨てた理由

- **Go方式(括弧内も継続トークン必須)**: 規則は1本だが「最終引数のトレーリングカンマ忘れ」がTS育ちの人間・AIの定番エラーになる。
- **UI語の完全予約**: 規則は単純だがUIを使わないBEコードにもコストを課す(`state` は頻出変数名)。

## Assumptions

- A-9(継続規則を単純に定義しきれる)を再更新: 例外は「後置`?`の除外(0026)+括弧深度(本ADR)」の2つで確定。

## 既存ADRとの相互作用

- ADR-0026: 「のみ」リストの具体化・拡張(`.`/`..`/キーワード演算子/複合代入を追加)。後置`?`の終端規則は不変。
- ADR-0003(UI組み込み構文): 文脈キーワード化により9章のcomponent文法設計に前提を与える(A-5と整合)。
- ADR-0028(`or e => { }`): 行末 `or` でも継続できるため、束縛形を行またぎで書ける。

## Consequences

- 字句解析器は括弧深度の**スタック**を持つ(`{` で退避・対応する `}` で復元)。
- 仕様1章(L-20〜L-22)に明文化済み。conformanceテスト `multiline-call` 等で固定する。
