# ADR-0021: 並行処理は「色なし」+選択的async出力

- **Status**: accepted
- **Date**: 2026-08-14
- **決定者**: ユーザー + Claude

## Context

Phase 1ラウンド5のQ17。JSの `async/await` は関数を2色に分け、awaitの書き忘れが静かなバグになる。一方で「全関数をasync出力する」素朴な色なし実装には実行コストがある。ユーザーの要望で決定前にベンチマークを実施した(benchmarks/async-overhead.mjs、Node 24 / Apple Silicon)。

**実測結果**: 最悪ケース(fib(25)、関数呼び出し24万回のCPU計算)で**15.2倍**遅い(0.49ms→7.43ms)。現実ケース(1万件の明細レンダリング)では**1.7倍**、絶対差+1.3ms/回。

## Decision

- **`async` / `await` を言語に露出しない**。ソース上はすべて同期に見え、待つ処理の管理はコンパイラの仕事とする。awaitの書き忘れというバグの類型を言語から消す。
- コード生成は**選択的async出力**: 呼び出しグラフを解析し、非同期なFFI/IOに(推移的に)届く関数だけをasync+await付きで出力する。純粋な計算関数は同期JSのまま出力し、ベンチの15倍問題を回避する。
- 高階関数など非同期性を静的に追いきれない箇所は**安全側(async扱い)**に倒す。
- `spawn` / channel など並行の詳細構文はここでは決めず、Phase 5(BE基盤)の設計時に別ADRで決める。

## 検討した代替案と捨てた理由

- **全async出力(シンプル優先)**: 実装は最単純だがCPU計算で15倍の実測。最初から選択的出力を設計に織り込む方が、後からの作り直しより安い。
- **async/await露出(TS流)**: AI学習データ最多で実行制御も明示的だが、2色問題とawait忘れバグを言語に輸入する。

## Assumptions

- A-13: 非同期性の推論(呼び出しグラフ解析+高階関数の保守的扱い)を、健全性を保ったまま実装しきれる。

## Consequences

- 関数型・関数値には内部的に「非同期に届きうるか」の属性が付く(言語には見せない)。
- FFIのextern宣言(ADR-0022)には同期/非同期の区別を明記させる(推論の起点になるため)。
- ベンチは benchmarks/ に保存し、コード生成実装後に再計測して選択的出力の効果を確認する。
