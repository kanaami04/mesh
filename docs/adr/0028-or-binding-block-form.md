# ADR-0028: orの束縛形は `or e => { 式 }`(ADR-0005規則5の精密化)

- **Status**: accepted
- **Date**: 2026-08-14
- **決定者**: ユーザー + Claude(設計監査 2026-08-14 の発見#4の決着)

## Context

ADR-0005規則5は束縛形を `or e => 式` と書いていたが、ADR-0025が確立したパーサ不変条件「`=>` の次は必ず `{`」と矛盾していた(監査で検出)。

## Decision

```
let age = parseAge(s) or 0                 // 素のor(none専用): 束縛なし・式のまま
let age = parseAge(s) or e => { log(e) }   // 束縛形: matchの腕と同型のブロック必須
let age = parseAge(s) or _ => { 0 }        // 意図的に捨てる形も同様
```

- 束縛形の本体は**ブロック必須**。ブロックの最後の式が値(if・matchと同じ規則)。
- これにより `=>` の意味は「**束縛付き本体の導入**」(matchの腕・orの束縛形)という1つの一般規則になり、「`=>` の次は必ず `{`」が全域で成立する。

## 検討した代替案と捨てた理由

- **式形のまま(`or e => 式`)**: 短いが不変条件が崩れ、`=>` の文法が2種類になる。
- **別記法(`or(e) 式` 等)**: 記法が1つ増えるだけで利点がない。

- (特になし)

## 既存ADRとの相互作用

- ADR-0005: 規則5の記法をこの形に精密化(方針は不変。素のorがnone専用・errorは束縛必須の規則も不変)。
- ADR-0025: パーサ不変条件「`=>` の次は必ず `{`」を維持・強化。
- ADR-0026: `=>` は行継続トークン(行末の `=>` は継続)。orの束縛形を行またぎで書ける。

## Consequences

- `or` の優先順位と結合方向(`f() or g() + 1` の解釈、`or` の連鎖)は仕様3章で確定する(監査#の残項目)。
