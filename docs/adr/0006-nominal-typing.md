# ADR-0006: 型の同一性は名前的に決める

- **Status**: accepted
- **Date**: 2026-08-13
- **決定者**: ユーザー + Claude

## Context

Phase 1ラウンド1のQ3。形が同じ型(例: `UserId` と `ItemId`、中身はどちらも `{ value: int }`)を同じ型として扱うか、別の型として扱うかを決める必要があった。

## Decision

**名前的型付け**を採る。形が同じでも型名が違えば別の型。取り違えはコンパイルエラーになる。

## 検討した代替案と捨てた理由

- **構造的(TS流)**: 柔軟でTSユーザーには馴染み深いが、意図しない型の一致が素通りする。エラーメッセージが「構造の差分説明」になり難解化しがち。
- **名前的+interfaceだけ構造的**: 同一性の規則が言語に2つ入り、説明コストが増える。interface自体の要否は抽象化の議論(後続ラウンド)で別途決める。

## Assumptions

- A-8: 名前的型付けがAIのコード生成成功率を大きく損なわない(学習データの主流であるTS=構造的からの負転移が許容範囲に収まる)。

## Consequences

- エラーメッセージを「`UserId` が必要ですが `ItemId` が渡されました」と型名で明快に書ける(style-guide原則4と整合)。
- FE/BEの型共有は「同じ型定義を両側でimportする」形になる(構造が同じ別定義では代用できない)。
- unionメンバーの実行時判別(A-7の型タグ)も名前ベースで設計でき、整合する。
