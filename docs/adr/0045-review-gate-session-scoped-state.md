# ADR-0045: レビューゲートの状態をセッション別に分け、レビュー済み記録は追記のみにする

- **Status**: accepted
- **Date**: 2026-08-17
- **決定者**: ユーザー + Claude

> 採番の注記: 本ADRを起票した時点で ADR-0044「数字直後の `.` の帰属」が別セッションで進行中だったため、番号衝突を避けて 0045 を取った。前提IDも同様に衝突したため(双方が A-22 を主張)、先に起票された ADR-0044 側を A-22 とし、本ADRの前提を A-23 に改番した。

## Context(何を決める必要があったか)

doc-review・impl-review のStopフックが、**同一の作業ツリーで複数のClaude Codeセッションが並行して動くと、レビューを取りこぼす**ことが実地で判明した。

2026-08-17、3セッション(w2/w3/w4)が同じ `/Users/kanayama/kanaami/language` を共有した状態で、次が起きた。

1. セッションw3がコード変更 `4426053` をコミットした
2. **無関係なセッションw4**のStopフックが発火し、そのコミットについてブロック通知を出した
3. 通知の副作用でマーカーが `4426053` まで前進した
4. 結果、w3自身のStopフックは何も検知しなくなった

原因は2つあり、どちらも単独で欠陥である。

**原因1: 状態がセッション間で共有されている。** doc-reviewは `.claude/.doc-review-marker` のmtime、impl-reviewは `.claude/.impl-review-marker` のコミットハッシュを、全セッションが読み書きしていた。片方のレビューがもう片方の検知をリセットする。

**原因2: ブロックの副作用で「レビュー済み」に昇格していた。** 両フックともロックアウト防止のためブロックと同時にマーカーを前進させていた。これは**セッションが1つでも成立する穴**で、通知を無視して完了すれば未レビューのコードが恒久的に緑になる。

## Decision(何に決めたか)

状態を「誰の話か」で3種類に分け、**レビュー済みの記録はレビューを実行した者だけが追記する**。

| ファイル | 範囲 | 書く人 |
|---|---|---|
| `.claude/state/touched-<session_id>` | セッション別 | PostToolUseフック(編集のたび) |
| `.claude/state/impl-reviewed-commits` | 共有・追記のみ | impl-reviewスキル(実行後) |
| `.claude/state/impl-exempted-commits` | 共有・追記のみ | impl-reviewスキル(ユーザー免除時) |
| `.claude/state/impl-notified-<session_id>` | セッション別 | Stopフック(通知のたび) |

**doc-review**: mtime比較をやめる。PostToolUseフック `record-touched.sh` が `Edit|Write|NotebookEdit` の `file_path` をセッション別に記録し、Stopフックは**そのセッションが実際に編集した `.md`** だけを検査する。

**impl-review**: 「レビュー済み地点を指すポインタ」をやめ、**レビュー済みコミットの集合**にする。Stopフックは `merge-base(origin/main, HEAD)..HEAD` のコード変更コミットのうち、レビュー済みでも免除済みでも通知済みでもないものを検出する。ブロック時に書くのは**通知台帳だけ**で、レビュー済み台帳には触れない。

ロックアウト防止は維持する。同じコミットで無限にブロックされないよう、通知は「(セッション, コミット)の組につき1回」に限る。

## 検討した代替案と捨てた理由

**案A: マーカーをセッション別にするだけ(最小変更)。** すり抜けは消えるが、他セッションが編集したファイルでも自分がブロックされる過剰ブロックが残る。またimpl-reviewの原因2(通知を無視すれば緑)がまったく解決しない。棄却。

**案B: git worktreeでセッションごとに作業ツリーを分ける。** 衝突の根本原因である共有そのものを断つ最も強い手で、実際に運用として併用する価値がある。ただし**フックの欠陥(原因2)はworktreeでは直らない**。1セッションでも穴が開いたままなので、フック側の修正は必要。運用とフックは独立した対策として両方採る。

**案C: git のコミット trailer にセッションIDを埋めて誰のコミットか判別する。** コミット単位で持ち主を特定できるが、コミット作成経路すべてにtrailerを強制する必要があり、手で打ったコミットが漏れる。台帳方式なら持ち主の特定自体が不要になるため棄却。

## Assumptions(この決定が依存している前提)

- **検証済み**: Claude CodeのフックはstdinのJSONで `session_id` を受け取れる(Stop・PostToolUseとも。2026-08-17に公式ドキュメントで確認)
- **検証済み**: モデル側は環境変数 `CLAUDE_CODE_SESSION_ID` で同じ値を参照できる(スキルが自分の記録を消すために必要)。2026-08-17に、env の値がトランスクリプト `~/.claude/projects/<project>/<session_id>.jsonl` のファイル名と一致することを実測して確認した
- **未検証(A-23)**: `.md` の更新は `Edit` / `Write` / `NotebookEdit` を経由する。シェル経由で生成・書き換えられた `.md` は記録されない(既知の限界。ASSUMPTIONS.md の A-23 に登録)

## 既存ADRとの相互作用

- **マージ可能ルール(CLAUDE.md)との相互作用**: 旧方式は「squashマージでハッシュが変わるとマージコミットが未レビューと誤検知される」ためマージ後のマーカー更新を義務づけていた。新方式ではmainブランチがフック対象外である事実が変わらないため、この追加作業は不要になる。impl-reviewスキルから当該手順を削除した。
- **仕様ADR群との相互作用はない**。本ADRは開発ワークフローの決定であり、Mesh言語の仕様には触れない。

## Consequences(この決定の帰結・影響)

- **利点**: 同一作業ツリーで複数セッションが動いてもレビューが取りこぼされない。通知を無視したまま完了することができなくなる。doc-reviewがmtimeに依存しなくなり、pull/checkoutによる誤検知を防ぐためのガード(`git status --porcelain -- '*.md'`)が不要になった。
- **コスト**: PostToolUseフックが1つ増える(編集のたびに実行されるため軽量に保つ)。`.claude/state/` にセッション別ファイルが蓄積するので、定期的な掃除が要る。
- **移行時の一度きりの影響**: 旧マーカーは参照されなくなるため、既存ブランチのコミットが一度だけ「未レビュー」として再通知される。
- **worktree運用は引き続き推奨**。本ADRは共有作業ツリーでの安全性を上げるが、1作業ツリー = 1ブランチというGitの制約は解消しない。別ブランチで並行作業するなら作業ツリーを分ける必要がある。
