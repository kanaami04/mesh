# ADR-0047: 閉じ括弧は同種とだけ対応させ、`!==` にも誤綴り誘導を出す

- **Status**: accepted
- **Date**: 2026-08-18
- **決定者**: ユーザー + Claude

字句解析器の再レビュー(ADR-0046の分担で実施)で出た2件の指摘に対する決定。どちらも**エラーメッセージ品質**が理由である。

## Context(何を決める必要があったか)

### 1. 括弧深度スタックが閉じ括弧の種類を照合していなかった

L-21のため、字句解析器は「いま `(` か `[` の内側にいるか」をスタックで持つ。実装は閉じ括弧なら種類を問わず `pop` していた。釣り合った入力では pop 先が必ず一致するため観測できないが、**釣り合わない入力で文の区切りが壊れる**。

実測(2026-08-18):

```
call(
  fn()
    a
  }
)
```

`{` の書き忘れ。`}` が `(` を pop するため「括弧の外に出た」と誤認し、`}` の直後に文の区切りを挿入する。閉じ波括弧を余分に打った場合(`call(\n a\n }\n b\n)`)は区切りが3個入り、引数リストが3つの文に割れる。

L-21は「深度は `{` で退避し、**対応する** `}` で復元する」と書くが、`)` が `[` を閉じてよいかを直接規定していなかった。

なお同一ファイル内の `scan_interpolation` は `Vec<TokenKind>` で**すでに種類照合している**(`"${(]}"` を正しい位置で E0109 と報告する)。厳密さの違う括弧スタックが2実装ある状態だった。

### 2. `!==` に誤綴り誘導が無かった

L-26は `===` に「等価比較は `==`」の案内を定めるが、`!==` を列挙していなかった。実測では `a !== b` は `Ident BangEq Eq Ident` に分解されて字句を素通りする。パーサは3文字目の `=` を指すことになり、**同じ種類の間違いなのに `===` だけ手厚い非対称**が生じていた。JS/TS出身者とAIが最も打ちやすい綴りである。

## Decision(何に決めたか)

1. **閉じ括弧は同種の開き括弧とだけ対応する。** スタックの先頭が同種でなければ深度を戻さない。`lex` を `scan_interpolation` と同じ方式へ寄せ、括弧照合の二重実装を解消する。
2. **`!==` を L-26 の誘導一覧に加える。** 「非等価比較は `!=`」を案内し、負例conformance ID `triple-not-equals` を予約する。

## 検討した代替案と捨てた理由

**案A(1について): 現状維持し、パーサ側で不均衡を検出したときに補正する。** 壊れた入力でしか発現せず、パーサはいずれ拒否するため実害は限定的。しかし本プロジェクトはパーサを手書き再帰下降にした理由を「エラーメッセージ品質を最優先」と定めており(CLAUDE.md)、**エラー位置が本当の原因から離れる**のは避けたい欠陥である。字句側の修正は数行で済むため棄却。

**案B(1について): 字句側で括弧の不均衡自体をエラーにする。** 種類の食い違いをその場で報告できるが、字句解析器の責務を越える。不均衡の報告はパーサの担当(EOF時にスタックが残っても字句は黙って捨てる、という既存の設計判断)と整合しない。棄却。

**案C(2について): JS由来の誤綴りをまとめて洗い出してADR化する。** `&&`/`||`(Meshは `and`/`or`)、`++`/`--` なども候補になる。網羅的で筋は良いが、今回の再レビューの範囲を越え、各案内文の妥当性を個別に詰める必要がある。`!==` は `===` と対になる明白な抜けなので先に埋め、残りは別途扱う(roadmapに記録)。

## Assumptions(この決定が依存している前提)

- 括弧の不均衡そのものはパーサが報告する(字句解析器はEOF時に非空スタックを黙って捨てる既存設計を維持する)
- `!==` を打つ利用者は非等価比較を意図している(`!` と `==` を続けて書く正当な構文はMeshに存在しない)

## 既存ADRとの相互作用

- **ADR-0031(継続一覧・括弧深度)との相互作用**: 深度スタックの導入元。本ADRはその pop 条件を精密化するもので、決定を覆さない。`{` で退避し `}` で復元する挙動は変わらない。
- **ADR-0046(実装の子セッション委譲)との相互作用**: 本ADRの2件は、ADR-0046で定めた分担(司令がレビュー、子が実装)で実施した最初の再レビューの成果である。
- **ADR-0010(改行区切り)との相互作用**: 文の区切りをどこに入れるかの規則そのものには触れない。壊れた入力での区切り位置だけが変わる。

## Consequences(この決定の帰結・影響)

- **利点**: 括弧を打ち間違えたとき、引数リストの途中に文の区切りが入らなくなり、パーサのエラーが本当の原因を指しやすくなる。`!==` に `===` と同等の案内が出る。
- **挙動が変わる範囲**: **釣り合わない括弧を含む入力のみ**。正しく釣り合った入力のトークン列は変わらない。
- **コスト**: `lex` の pop 条件に1分岐、`next_token` に `!==` の1分岐。いずれも小さい。
- **残した課題**: JS由来の誤綴り(`&&`・`||`・`++`・`--` 等)の網羅的な洗い出しは未着手。roadmapに記録する。
