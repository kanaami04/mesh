# ADR-0022: JS相互運用は宣言的FFI+境界検証(無検証のJS値は言語内に入らない)

- **Status**: accepted
- **Date**: 2026-08-14
- **決定者**: ユーザー + Claude

## Context

Phase 1ラウンド5のQ18。npm資産(地図・グラフ・日付処理)を使えないと実用アプリの道が遠のく一方、TSの `any` のような無検証の抜け穴は「AIの書いたコードが型でほぼ守られる」という言語の売りを壊す。前プロジェクトでは未決のまま最後まで刺さった穴だった。

## Decision

- `extern` 宣言でJS関数のシグネチャを宣言して呼ぶ(モジュール指定つき。例: `extern "npm:dayjs"`)。宣言には同期/非同期の区別を明記する(ADR-0021の推論の起点)。
- JSから入る値は不透明な `js.Value` 型として受け取る。**中身を使うには検証つき変換(`js.decode<T>(v)` は `T | error` を返す)が必須**。無検証でMeshの型に化ける経路を作らない。
- Mesh→JSへ渡す方向は型情報があるのでそのまま渡せる(nullやundefinedへの変換規則はADR-0005の正規化に従う)。

## 検討した代替案と捨てた理由

- **TS流の自由import(型定義を信頼)**: 手軽だが型定義が実態とずれた瞬間に静かに壊れる。`any` 問題の再来で「抜け穴の無さ」が崩れる。
- **FFIなし**: 言語は純粋に保てるが実用アプリが書けない(前実装で実証済みの行き止まり)。

## Assumptions

- A-14: extern宣言+検証つき変換の手間が、npmライブラリ利用の摩擦として許容範囲に収まる(よく使うライブラリは標準ラッパーの提供で緩和できる)。

## Consequences

- JSON APIの受信(ADR-0005のJS境界正規化)とFFIが「検証つきの門」という同じ設計原則に揃う。
- 型の恩恵が及ばない領域が `js.Value` の周りに局在し、レビュー・AIが注意すべき箇所が字面で分かる。
- 頻出npmライブラリの検証済みラッパー集を標準で持つかはPhase 5で検討する。
