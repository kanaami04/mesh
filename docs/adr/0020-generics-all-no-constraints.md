# ADR-0020: ジェネリクスは fn/struct/type すべてで使える(制約なし)

- **Status**: accepted
- **Date**: 2026-08-14
- **決定者**: ユーザー + Claude

## Context

Phase 1ラウンド4のQ16。前プロジェクトは「fnのみ対応」に限定した結果、`struct Box<T>` や `type Paged<T>` が書けず、意味論棚卸しで「FE対応の最大の壁」(UIコンポーネントの合成・メッセージ型のパラメータ化が頭打ち)と診断された。結論も「type/structへ最小限広げよ——制約なし・データの器だけ」だった。この教訓を最初から反映する。

## Decision

```
fn first<T>(xs: list<T>) T | none { ... }
struct Box<T> { value: T }
type Paged<T> = ...              // Tを使ったunion・別名
```

- 型パラメータは fn・struct・type のすべての宣言で使える。
- **制約(bound)は置かない**。`T` は完全に抽象で、`T` の値に対してできるのは「受け取る・保持する・渡す・返す」のみ。
- 実行表現は型消去(JSでは全部ただの値。実行時コストゼロ)。

## 検討した代替案と捨てた理由

- **fnのみ(段階導入)**: 前実装で壁になると実証済みの道。
- **制約付き(trait/interface bound)を最初から**: 抽象化の天井は上がるが、仕様・型検査器・エラーメッセージが大幅に膨らむ。v1のシンプルさ方針と合わない。必要が実証されたら新ADRで導入を検討する。

## Assumptions

- A-12: 制約なしジェネリクスでも、標準ライブラリの主要操作(sortの比較、mapのキー等値)は組み込み関数側の対応で賄える。

## Consequences

- 「比較できるT」が書けないため、`sort` 等は組み込み・標準ライブラリ側で型を限定して提供する(A-12)。
- UI構文(Phase 6)でメッセージ型・子コンポーネント型のパラメータ化が最初から可能になる。
