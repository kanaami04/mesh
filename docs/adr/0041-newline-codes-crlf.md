# ADR-0041: ソースの改行はLFとCRLFを受理し、単独CRは専用エラーにする

- **Status**: accepted
- **Date**: 2026-08-15
- **決定者**: ユーザー + Claude

## Context(何を決める必要があったか)

仕様1章は改行コード(LF/CRLF)を定めていなかった。字句解析器の改行実装(PR #17)のimpl-reviewで、2観点のレビュアーが独立に同じ穴を指摘した: Windowsのエディタや `git config core.autocrlf=true` で作られた `.mesh` は行末が `\r\n` になり、現実装では1行目の `\r` がE0116「どの字句規則にも該当しない文字」で落ちる。エラーが指すのは画面に見えない1バイトで、エラーメッセージ品質を最優先とする方針(vision)に反する。

## Decision(何に決めたか)

1. Meshソースの改行は **LF(`\n`)またはCRLF(`\r\n`)**。CRLFは1個の改行として扱う(字句上は1個のNewlineトークン。textは生の字面 `"\r\n"`、spanは2バイト)。
2. **単独のCR**(直後が `\n` でない `\r`)は専用エラー **E0117**「改行コードが不正です。LF または CRLF を使ってください」。
3. **Unicode改行類**(U+0085 NEL・U+2028 LS・U+2029 PS)は改行とみなさない(L-26のE0116対象のまま)。

仕様1章に L-29 として明文化する。

## 検討した代替案と捨てた理由

- **入力段で `\r\n`→`\n` に正規化**: 実装は最も楽だが、正規化後のオフセットが元ファイルと1行ごとに1バイトずれ、エラー位置・将来のエディタ連携(LSP)の品質を損なう。位置品質優先の方針と相性が悪く不採用。
- **拒否(LFのみ)**: 仕様は最もシンプルだが、Windowsユーザーとgit autocrlf環境で最初の体験が悪い。Go/Rust/Swift/TSがいずれもCRLFを受理する実用路線に合わせ不採用。
- **単独CRも改行として受理**(旧Mac形式): 現代に実例がほぼ無く、受理すると「見えない文字の違い」で挙動が変わる余地を増やすだけなので不採用。専用エラーで案内する。

## Assumptions(この決定が依存している前提)

- A-18: Newlineトークンのtext差(`"\n"` / `"\r\n"`)を後段(パーサ・fmt・コード生成)が区別せずに扱える(ASSUMPTIONS.md参照)。

## 既存ADRとの相互作用(2026-08-14監査の教訓により必須)

- **ADR-0010(改行=文終端、Go方式)**: CRLFも「1個の改行」として同じ終端規則に乗る。矛盾なし。
- **ADR-0026(行継続)・ADR-0031(継続一覧・括弧深度)**: 継続判定は「行末のトークン」に対して行うため、改行が1トークンである限り改行コードの違いは影響しない。
- **仕様1章L-16(文字列中の生の改行=E0108)**: 文字列リテラル内の `\r\n`・`\r` も「生の改行」側の扱いになる(E0108の検出対象に `\r` を含める)。文字列実装のサイクルで適用する。
- **token()の不変条件(text==source[span])**: textを生の字面 `"\r\n"` で保持するため維持される。`"\n"` への正規化はここでは行わない(正規化するとtextとspanの長さが食い違う)。

## Consequences(この決定の帰結・影響)

- 仕様1章1.8に **L-29** を追加(正例: `crlf-newline` / 負例: `lone-cr`)。E0117を字句エラーコード表に追加。
- 字句解析器は `\r` を読んだら直後の `\n` を確認し、あればまとめて1個のNewline、なければE0117を報告する。
- JS出力(コード生成)には影響しない(改行トークンの後段の扱いはtext非依存=A-18)。
- `mesh fmt`(Phase 8)は出力改行コードの統一を検討する(このADRの範囲外)。
