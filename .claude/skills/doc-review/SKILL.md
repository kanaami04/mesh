# doc-review — 変更単位のドキュメントレビュー

**発動条件**: 設計文書(docs/以下・CLAUDE.md・README.md)に意味のある変更を加えた作業の締め。typo修正だけの場合は不要。ユーザーの指示を待たず自発的に実行する。

## 手順

### 1. 変更範囲の特定

`git status` / `git diff`(未コミットならワーキングツリー、コミット済みなら直近コミット)で今回変更されたmdを列挙する。

### 2. 関連文書の読み込み

変更ファイルごとに「参照している文書」「参照されている文書」を辿る(最低限: 関連ADR、spec該当章、docs/adr/ASSUMPTIONS.md、索引類)。全文書は読まない——それはdrift-checkの仕事。

### 3. 5つの検査

| # | 検査 | 見るもの |
|---|---|---|
| 1 | **設計整合** | 変更内容が既存ADRの決定と矛盾しないか。**単体で正しくても組み合わせで穴が開かないか**(例: 新しい後置記法×行継続規則ADR-0026。2026-08-14監査の教訓) |
| 2 | **正文書ルール** | ADRの裏付けなしに「決定済みの顔」をした記述を足していないか。決定を含むなら `adr` スキルへ |
| 3 | **参照整合** | 索引・台帳の更新漏れ(ADR追加時のREADME一覧・ASSUMPTIONS)、リンク切れ、章番号のずれ |
| 4 | **文言品質** | docs/style-guide.md のセルフチェックリスト(結論先出し / 一文一義 / 専門用語の初出説明 / 「等」「適切に」逃げ / 見出しの拾い読み) |
| 5 | **サンプルコード** | 文書内のコード例が最新の決定と一致しているか(旧記法の残存が典型drift。実例: `type User struct` がADR-0012後も残っていた) |

### 4. 独立レビュアーの起用判断

- **新ADR・仕様章の追加・決定変更**を含む変更: 検査1のみサブエージェント(先入観のない敵対的レビュアー)に委譲し、結果をメインの検査と突き合わせる。プロンプトには「関連ADR番号」「矛盾・相互作用バグを具体的なコード例で示せ」「深刻度を『覆す必要/規則追加で解決/軽微』で分類せよ」を含める。
- それ以外の変更: メイン自身がチェックリストで検査(サブエージェントは使わない。コストに見合わない)。

### 5. 結果の処理

- **軽微(typo・リンク切れ・索引漏れ・スタイル違反)**: その場で修正し、修正内容を報告に含める。
- **設計に触れる指摘(矛盾・相互作用の穴・未ADRの決定)**: 勝手に直さず「場所・問題・修正案」の形でユーザーに報告し、判断を仰ぐ。
- 指摘ゼロなら「doc-reviewクリア」と一言で報告する(長い報告を書かない)。

## drift-checkとの役割分担

| | doc-review(このスキル) | drift-check |
|---|---|---|
| タイミング | 変更のたび(自発) | フェーズ完了時・大変更後 |
| 範囲 | 変更ファイル+関連文書のみ | 全ADR×全文書 |
| コスト | 軽い | 重い |

## やらないこと

- 全文書の総当たり検査(drift-checkの担当)
- 設計判断そのもの(指摘と修正案の提示まで。決定はユーザー+adrスキル)
- コード(.rs等)のレビュー(コードレビューは別の仕組み)
