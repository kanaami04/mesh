# spec-write — 仕様章の執筆手順

このスキルは**手順のみ**を定める。フォーマットの定義(4点セット等)の正は docs/spec/overview.md の「仕様の書き方ルール」であり、ここには重複させない。

## 手順

### 1. 対象章と根拠の確定

- docs/spec/overview.md の状態表で対象章と、その「✅方針」の根拠ADR番号を確認する。
- docs/adr/README.md の索引から関連ADRを読む(Status: superseded は除く。精密化ADRは番号の新しい方が勝つ)。
- docs/design-audit-*.md の「仕様執筆時に明文化リスト」から対象章の項目を拾う。

### 2. 執筆

- 章ファイルは `docs/spec/NN-英小文字名.md`(例: `01-lexical.md`)。
- 書式は overview.md の書き方ルールに従う。とくに:
  - 決定はEARS風の規範文に**書き直す**(ADRの文言のコピペではなく「〜のとき、コンパイラは〜すること」の形へ)。
  - 正例・負例はセット。負例には期待されるエラー(位置・種類・可能なら修正候補)を書く。
  - **各負例に conformanceテストIDを予約として明記**する(`tests/NN-章名/ケース名` 形式)。
- 執筆中に未決事項が見つかったら**勝手に決めない**。TBDと明記し、決定が必要ならユーザーに確認して `adr` スキルへ。

### 3. 相互参照と消化

- 章の各節から根拠ADRへリンクする(読者が「なぜ」に遡れるように)。
- 監査文書の明文化リスト項目を消化したら、監査文書側に「→ 仕様NN章で明文化済み」と追記する。

### 4. 更新と締め

- overview.md の状態表を「✅執筆済み(章リンク)」へ更新する。
- 言語カード(作成後)に影響する変更ならカードも同時に更新する。
- 最後に **`spec-review` スキル**(敵対的レビュー+検証ラウンド)で締める。軽微な修正のみの改訂なら `doc-review` で足りる。
  - **執筆を子セッションへ委譲した場合の例外**(`orchestrate`): 子は執筆までを行い、`spec-review` は**司令が `opus` で回す**。GLMセッションではサブエージェントのモデル指定が効かないため(ADR-0046)。

## 完了チェックリスト

- [ ] 根拠ADRの全決定にEARS文が対応している(決めたのに書いていない規則が無い)
- [ ] 正例・負例がセットである(負例の無い節を作らない)
- [ ] すべての負例にテストIDが予約されている
- [ ] ADRと矛盾する記述が無い(矛盾に気づいたらADRが正。spec側を直すか、覆すなら新ADR)
- [ ] 監査の明文化リストの該当項目を消化し、消化済みマークを付けた
- [ ] overview.md の状態表を更新した

## やらないこと

- 新しい設計判断(`adr` スキルとユーザー確認の担当)
- テストの実装(実装フェーズの `tdd` スキルの担当。ここでは対応表の予約まで)
- フォーマット規則の再定義(overview.mdが正)
