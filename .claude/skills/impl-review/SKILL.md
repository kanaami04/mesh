# impl-review — 実装の変更単位レビュー

**発動条件**: src/・tests/・Cargo.toml に変更をコミットした作業の締め(push後、マージ依頼の前)。ユーザーの指示を待たず自発的に実行する。Stopフックが未実施を検知してブロックするため、忘れても機械的に発動する。

## 手順

### 1. 差分の特定

`git diff main...HEAD -- src tests Cargo.toml` で今回のコード差分を取得し、関連する仕様章(docs/spec/)・ADR・test-writingスキルを列挙する。

### 2. 敵対的レビュー(並列2観点)

サブエージェント2体を**opus**で並列起動する(モデル使い分け規約: 敵対的レビューは非自明タスク)。共通の指示: 「LGTMを出すことが目的ではなく欠陥を見つけることが目的。指摘ゼロで返す場合は、検査した観点と『問題なし』の根拠を列挙すること(根拠なしの合格は不可)」。

- **観点A: 仕様適合とテストの穴** — 差分と該当仕様章の規則(EARS文・正例・負例)を突き合わせる。仕様が定めるのにテストが無いエッジケース、conformance負例IDとの対応漏れ、test-writing規約違反(曖昧検証・期待値の非明示・命名)を探す。
- **観点B: 実装品質** — UTF-8/バイト境界、オフセット計算のずれ(off-by-one)、panic経路、不変条件の破れ(例: `token.text == &source[span]`)、Rustイディオム、clippyが拾わない設計上の弱点を探す。

渡すもの: 差分全文 / 変更ファイルの全文パス / 関連仕様章のパス / .claude/skills/test-writing/SKILL.md / 検査観点。

- 縮退則: 差分が tests/ のみ(プロダクトコード無変更)の場合は**観点Aの1体**でよい(観点BのUTF-8境界・panic経路検査はsrc/の変更を対象とするため)。

### 3. 指摘の分類と処理

| 深刻度 | 基準 | 処理 |
|---|---|---|
| **重大** | 誤動作・仕様違反・不健全なAPI | `tdd` スキルで修正(再現テストRed→Green)。テスト無しの直接修正は不可 |
| **改善** | このPR内で直す価値がある品質問題 | メインが直接修正し、全テスト+fmt+clippyを再実行 |
| **メモ** | 将来サイクルの課題 | テストリストまたはdocs/roadmap.mdに追記(このPRでは直さない) |

### 4. 解消検証

重大・改善を修正したら、**同一レビュアー**(SendMessageで継続)に修正差分を渡して解消を確認する。新規指摘が出たら同様に処理。最大2ラウンドで収束しなければユーザーに判断を仰ぐ。

- 収束の軽量則(初回実走 2026-08-15 の学び): 検証ラウンドで出た新規指摘が**文書・コメントのみ**で、修正内容をレビュアーの提示文言と機械的に突き合わせられるなら、メインが修正・確認して収束宣言してよい。追加の検証ラウンドは重大・実装変更を伴う指摘が出たときだけ回す。

### 5. マーカー更新(必ず最後に)

```
git rev-parse HEAD > .claude/.impl-review-marker
```

修正コミットをすべて済ませた**後の**HEADを記録する(Stopフックはこのハッシュ以降のコード変更コミットを未レビューとみなす)。

## 例外(レビューを回さないケース)

- **コード変更が無い作業**(md・docs等のみ): フックが自動で素通しする。何もしなくてよい。
- **ユーザーが「レビュー不要」「レビュースキップ」と明示したとき**: レビューを省略し、マーカーだけ更新して、報告に「impl-review免除(ユーザー指示)」と明記する。
- **mainブランチへの直接コミット**(ユーザー指示時のみ発生): フック対象外。必要ならユーザーが手動で依頼する。
- 自明な機械的変更(fmt整形のみ・コメント修正のみ)でも、省略はユーザーに確認してから。自己判断で免除しない。

## 位置づけと役割分担

- **doc-review**(文書)/ **spec-review**(仕様章)/ **impl-review**(実装)の3本目のレビュー機構。
- tddスキルとの関係: tddは「テストに書いた挙動」を守る仕組み。impl-reviewは「テストリスト自体の穴」(仕様の見落とし・エッジケース欠落)と実装の質を検査する補完。
- より重い網として `/code-review ultra`(クラウド多エージェント・課金・**ユーザー起動のみ**)がある。フェーズ完了級の節目ではultraの実行をユーザーに提案する。

## やらないこと

- md文書のレビュー(doc-reviewの担当)
- 設計判断の変更(指摘があればユーザー+adrスキルへ)
- スコープ外の"ついで修正"(メモとして残すだけ)
