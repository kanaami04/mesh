# TDD実装ワークフロー

1サイクル = **Red(失敗するテスト)→ Green(最小実装)→ Refactor(整える)** を、1振る舞い/1バグ単位で回す。このスキルは「コードをどう書き進めるか」のみを扱う。コミット・push・PR作成は呼び出し元の責任。

## Step 0: 前提の把握とテストリスト

**(a) プロジェクト設定の発見**(この順で探し、見つかった時点で止める):
1. プロジェクトの `CLAUDE.md` / `AGENTS.md`(テストコマンド・配置規約・フレームワーク)
2. ビルド設定(`package.json` scripts / `Cargo.toml` / `pyproject.toml` / `go.mod` など)
3. 既存テストの配置と書き方(規約はコードに倣う)
4. どれでも不明ならユーザーに確認(推測で走らない)

**(b) テストリストの作成**: 実装する振る舞いを「入力→期待出力」の粒度で箇条書きにし、TodoWriteまたはチャットで見える形にする。サイクル中に思いついた振る舞いは**その場で実装せずリストに追記**する。1項目の粒度は「1サイクルが5〜30分でGreenになる」程度。

## 適用判断

| TDDを適用する | 適用しない/限定する |
|---|---|
| ロジック(純粋関数・ドメイン・サービス層) | UIの見た目調整(E2Eは後でまとめる方が現実的) |
| データ変換・バリデーション・計算 | 設定ファイル・マイグレーションのみの変更 |
| API・コンパイラ等の入出力契約 | ドキュメントのみの変更 |
| バグ修正(再現テスト→修正) | 外部API/GPU/本番依存部分(モック境界の内側だけTDD) |

迷ったら具体案つきでユーザーに確認する(「この部分はTDD、UI部分は実装後にE2E、でよいですか?」)。

## 役割分担

テストを書く頭と実装を書く頭を分離し、「Greenを急いでテストを緩める」帳尻合わせを構造的に防ぐ。

| 役割 | 担当 | 禁止事項 |
|---|---|---|
| **メイン** | テストリスト管理 / 委譲 / **Refactor** / 完了判定 | Redサイクル中の実装コード執筆 |
| **Redサブエージェント** | 失敗するテストを1つ書き、失敗を確認 | プロダクトコードの実装(スタブを除く。下記) |
| **Greenサブエージェント** | テストを通す最小実装 | **テストの期待値・入力の変更(1文字も)** / スコープ外編集 |

サブエージェント機構が無い環境では、メインが「これからRedモード。実装は書かない」と**モード宣言**して同じ境界を守る。効果は機構ではなく境界の明確化にある。

## サイクル

### 1. Red — 委譲テンプレ

```
役割: TDDのRedフェーズ専任。失敗するテストを1つ書く。
検証する振る舞い: <入力→期待出力を具体的に>
参照: <既存ファイル・型・スキーマのパス> / テスト配置規約: <規約> / テストコマンド: <コマンド>
禁止: プロダクトコードの実装。テストが最初から通る状態で書くこと。
     曖昧な検証(toBeTruthy等)。期待値は具体的な値で書く。
スタブ規則(コンパイル言語のみ): テストがコンパイルできない場合に限り、
     対象の関数シグネチャ+意図的に失敗する中身(todo!()/panic/ダミー値)だけ追加してよい。
     ロジックは1行も書かない。
成功条件: テストを実行し、assertion error等で「意図した理由で」失敗していること。
     コンパイル/importエラーで落ちている状態はRedではない。
返すもの: テストファイルパス / 実行コマンドと失敗出力(assertion部分) / 検証している振る舞いの要約
```

失敗しないテストが書けてしまったら、それは目的の振る舞いを検証できていない。Red側の責任で直し、失敗を踏み直す。

### 2. Green — 委譲テンプレ

```
役割: TDDのGreenフェーズ専任。既存のテストを通す最小実装を書く。
通すべきテスト: <ファイルパス> / 失敗出力: <assertion部分>
編集を許可するスコープ: <ファイル/ディレクトリ>
テストコマンド: 該当のみ: <コマンド> / 全体: <コマンド>
禁止: テストの期待値・入力の変更(1文字も) / スコープ外編集 / 既存テストを壊す /
     テストを緩める・スキップする方向の修正
方針: テストが緑になる最小限を書く。ハードコード可(一般化は次サイクルの三角測量で)。
テストに問題があると判断したら: 自分で直さずメインに差し戻す(理由と該当箇所を添えて)。
成功条件: 該当テストが緑、かつ既存テストも全て緑。
返すもの: 変更ファイル一覧 / テスト実行ログ(該当+全体)
```

### 3. Refactor — メインが担当(委譲しない)

- 全テスト緑の状態から、重複除去・命名改善・責務整理。**テスト側も対象**(セットアップの共通化など)。
- リファクタ中に新しい振る舞いの必要に気づいたら、**手を止めてテストリストに追記し、Step 1へ**。リファクタとロジック追加を混ぜない。
- 終わったら全テスト+lint/formatを実行して緑を確認。スコープ外の"ついで修正"はメモして別Issueへ。

### サイクルの終わり方

テストリストの次の1項目を選んでStep 1へ。リストが空になったら、全体テスト+lintを走らせて完了。

## スナップショット/ゴールデンテストとの併用

スナップショット(insta等)は期待値が自動生成されるため、古典的なRed(先に期待値を書く)が踏めない。使い分ける:

- **新しい振る舞いのTDDサイクル**: 期待値を明示するassertテストで回す(Redが踏める)。
- **スナップショット**: サイクル完了後の**回帰の網**として追加する(出力全体の固定)。初回生成されたスナップショットは必ず目視レビューしてからコミット対象にする。
- 例外: 「期待出力を先に手書きしたゴールデンファイル」を用意できるなら、それはRedとして成立する。

## バグ修正でのTDD

1. **再現テストをRedに依頼** — 不具合を表すテストを書かせ、現状コードで失敗することを確認(=再現)。再現できないなら原因切り分けが不十分。ユーザーに追加情報を聞く。
2. **最小修正をGreenに依頼** — 該当+周辺テストが緑になることを確認。
3. **メインがリファクタ** — 同型の不具合を防ぐ整理(型を厳しくする等)。スコープを超えない。

## やらないこと

- コミット・push・PR作成(呼び出し元の責任)
- 設計判断のやり直し(設計フェーズの責任。テスト方針が未合意なら設計に戻る)
- スコープ外のリファクタ・"ついで修正"
- 役割の越境(Redが実装ロジックを書く / Greenがテストを書き換える)

## 完了チェックリスト

- [ ] テストリストの全項目についてRedを踏んだ(テストが先・失敗を確認)
- [ ] Greenはテストを書き換えずに通した
- [ ] 全テスト+lintが緑
- [ ] テストの配置・命名がプロジェクト規約に沿っている
- [ ] スコープ外の変更を混ぜていない
- [ ] (該当時)スナップショットは目視レビュー済み
