# orchestrate — 実装を子セッションへ出し、判断とレビューを手元に残す

**司令(このセッション)は設計判断とレビューを持ち、実装は子セッションへ出す。** 司令はプロダクトコードを書かない。書いた瞬間にレビューの独立性が消えるため。

## なぜこの分担なのか(実測に基づく)

GLMセッションでは、サブエージェントの `opus` / `sonnet` 指定が `ANTHROPIC_SMALL_FAST_MODEL`(glm-4.7)へ**黙って落ちる**。2026-08-18の計測で18件中18件が転落した(ADR-0046)。エラーにならないため、ログを見ない限り気づけない。

ここから2つの規則が導かれる。

1. **GLM子セッションにサブエージェントを使わせない。** 分離が要るならセッションを分ける。
2. **レビューは司令が持つ。** impl-review・doc-review・spec-review の `opus` 委譲は、Claudeセッションでしか正しく動かない。

## 役割

| | 司令(Claude) | 子(GLM) |
|---|---|---|
| 担当 | 設計判断・ADR・仕様の確定・Red失敗理由の確認・Refactor判断・レビュー・PR | 下表の作業 |
| サブエージェント | `opus`/`sonnet` を明示指定して使う | **使わない** |
| 実際に動くモデル | セッションモデル | glm-5.3(セッション本体) |

**子(GLM)に出す作業**——判断ではなく作業であり、サブエージェント委譲が要らないものすべて。

| 作業 | 司令が先に固めるもの | 司令が後で受け取るもの |
|---|---|---|
| テスト実装(Red) | テストリスト(**期待値は書かない**) | 失敗理由の妥当性判断 |
| プロダクトコード実装(Green) | 失敗しているテスト | Refactor判断・レビュー |
| 仕様章の執筆(spec-writeの下書き) | 根拠ADR(確定済み) | `spec-review`(opus)での品質ゲート |
| 調査・実測・検証スクリプト | 何を測るか | 数値の解釈と結論 |
| `drift-check` の全量検査 | 検査範囲 | 判断が要る指摘の処理 |

**子に出してはいけないもの**: レビュー(impl-review / doc-review / spec-review)、ADRの起票、仕様の決定、PR作成。前3者は `opus` 委譲が必須で、後2者は設計判断そのもの。

コスト配分の考え方: 実装だけに絞るとGLMの枠が余る。**判断を伴わない作業は積極的にGLMへ出す**(2026-08-18のユーザー方針)。

## 1サイクルの回し方(TDDの場合)

**1サイクル = 1 worktree = 1ブランチ = 1 PR。**

実装以外の作業(仕様執筆・調査・drift-check)も骨格は同じ——司令が前提を固める → 子へ投入 → 司令が結果を判断する。違うのは4〜6の中身だけで、**レビューは常に司令が持つ**。

### 1. 司令: テストリストを作る

仕様章のEARS文・負例IDから「何を検証するか」を列挙する。**期待値は書かない**——ソースと期待するトークン種別の列までにとどめ、spanやオフセットの計算はRed子にさせる(2026-08-15の学び。期待値を渡すとテストが実装の写経になる)。

### 2. 子を立てる

```
mesh-wt --glm <branch> "<ラベル>"
```

worktree(`.claude/worktrees/<branch>`)・herdrワークスペース・GLMセッションが一度に立ち、エージェント名が返る。

**タスクを投入する前に、必ずモードを確認する。**

```
herdr agent read <名前> --source visible --lines 6
```

`⏸ manual mode on` と出たら、**ユーザーに `shift+tab` での切り替えを依頼する**(司令が代わりに承認を押さない——ユーザーの許可判断を迂回することになる)。`⏵⏵ auto mode on` を確認してから投入する。

投入してから気づくと、長いプロンプトが承認待ちで宙に浮く。2026-08-18の実運用で2回続けて踏んだ。

### 3. Red子へ投入する

```
herdr agent prompt <名前> "<指示>" --wait --timeout 600000
```

指示の冒頭に必ず入れるもの: **`.claude/skills/orchestrate/CHILD.md` を最初に読んで従うこと**、司令のセッション名(`jq -r .name ~/.claude/sessions/$PPID.json` で取る)。加えてテストリスト・対象仕様章のパス・「src/ は変更しない」。

**`--wait` の戻り値を信用しない。** 2026-08-18の実運用で2つの罠を踏んだ。

- **`--wait` は約10分で戻る。** 子が止まったのではなく、こちら側のタイムアウト。`herdr agent get <名前>` で `working` なら待ち続ける
- **`done` が返っても終わっていないことがある。** herdrの状態検出は承認待ちを取りこぼす。1回目は `done` を返しながら実際は編集の承認待ちだった

したがって、戻ってきたら**必ず実物を確認する**。

```
git -C <worktree> log --oneline -1     # コミットされたか
git -C <worktree> status --short       # 中途半端な変更が残っていないか
herdr agent read <名前> --source recent-unwrapped --lines 40   # 画面で最終状態を見る
```

### 4. 司令: Redの失敗理由を確認する

テストが**正しい理由で**落ちているかを見る。コンパイルエラーで落ちているのはRedではない。ここを飛ばすと、実装が無いのではなく書き間違いで落ちているテストを緑にしてしまう。

### 5. Green子へ交代する

Red子を終了させ、**同じworktreeで**Green子を立てる。Red子とGreen子を同時に走らせない(1作業ツリー = 1ブランチのため)。

```
herdr pane run <ペインID> 'cc-glm'
herdr agent rename <ペインID> <名前>
```

指示: 「テストを変更せず緑にする」「最小実装にとどめる」。CHILD.md の参照は同じ。

### 6. 司令: Refactorとレビュー

- `cargo test` / `cargo fmt --check` / `cargo clippy --all-targets` を**司令が自分で**確認する
- Refactorは司令が判断し、必要なら子へ差し戻す
- `impl-review` を司令が回す(`opus` 2観点)。レビュー済み台帳(`.claude/state/impl-reviewed-commits`)への追記は**作業対象のworktree側**で行う(`.claude/state/` は作業ツリーごとに独立するため、別の作業ツリーへ書いても効かない)
- レビュアーには**変異解析**(実装をわざと壊してテストが落ちるか見る)を促す。削除・置換だけでなく「**意味論の深さを変える / 条件を広げる**」型を含めるよう指示する——2026-08-18の再レビューで、後者だけが検出できた穴が2件あった(深追いpop・先読みの過剰一般化)
- レビュアーが報告した**数値は自分で実測してから**ADRや文書に書く。転記して誤った実例を1件出した(同日)
- md変更があれば `doc-review`

### 7. PR

マージ可能ルール(CLAUDE.md)に従い、司令がPRを作る。

## 連絡

- **往路**: `herdr agent prompt` で直接投入する。人のコピペは不要
- **復路**: 子から `SendMessage`。宛先は `ListAgents` の `名前 [ref]` の形。名前だけでは拒否される
- **受信の前提**: `crossSessionInbound: "accept"` が要る。**ユーザー設定(`~/.claude/settings.json`)か `/config` で設定する**——プロジェクト設定は「既定より厳しいときだけ」適用されるため、`accept` を書いても効かない。起動時に読まれるので、設定より前に始めたセッションでは有効にならない
- **疎通しないとき**: `herdr agent read <名前> --source recent-unwrapped --lines 120` で画面を読む。片方向だが進行は止まらない

## やらないこと

- 司令がプロダクトコードを書く(テストリストの作成までにとどめる)
- GLM子にサブエージェントを使わせる
- GLM子にレビュー(impl-review / doc-review / spec-review)をさせる
- Red子とGreen子を同時に走らせる
- 子が権限で拒否された操作を司令が代行する(権限の迂回になる。ユーザーへ返す)

## tddスキルとの関係

`tdd` はRedとGreenを**別サブエージェント**に分ける。このスキルは同じ分離を**別セッション**で作る。目的(テストが実装に引きずられるのを防ぐ)は同じで、粒度が違う。

実装を外へ出さないときは `tdd` をそのまま使う。司令セッション自身がClaudeなら、サブエージェント委譲は正しく動く。
