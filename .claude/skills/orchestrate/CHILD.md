# 子セッションへの定型指示

このタスクは司令セッションからの委譲です。**着手前にこの指示を読み、従ってください。**

## 守ること

- **サブエージェント(Agent tool)を使わないでください。** このセッションではモデル指定が効かず、`opus` と書いても最小モデルで実行されます(ADR-0046)。並列化したくなったら司令へ相談してください。
- **レビュースキル(impl-review / doc-review / spec-review)を実行しないでください。** 司令が担当します。同じ理由で、このセッションでは敵対的レビューが最小モデルで走ってしまいます。
  - コミット後の停止時に「レビュー未実施のコード変更コミットがあります」とブロックされることがあります(Stopフック)。**その通知は無視して構いません。**レビューは司令が行い、レビュー済み台帳への追記も司令が行います。通知が出た事実を完了報告に含めてください。
  - このブロックは同じコミットについて1セッションにつき1回だけです。作業が止まることはありません。
- **担当範囲の外を触らないでください。** Redなら `tests/` のみ、Greenなら `src/` を中心にテストは変更しない。仕様執筆なら `docs/spec/`、調査なら読み取りとスクラッチパッドのみ。
- 作業は**渡されたworktree内**で完結させてください。`/Users/kanayama/kanaami/language` 本体は触らないでください。

## 進め方

- テストの書き方は `.claude/skills/test-writing/SKILL.md` に従ってください(AAAマーカー・1テスト1assert・期待値明示)。
- 仕様の正は `docs/adr/`、次いで `docs/spec/`。矛盾があれば番号の新しいADRが勝ちます。自己判断で仕様を変えず、司令へ返してください。
- コミットは意味単位で。`cargo fmt` と `cargo clippy` を通してから完了報告してください。
- **PRは作らないでください。** 到達点は「コミット済み・意図どおりの状態」までです。レビューとPRは司令が行います。
- **ADRを起票したり仕様を決めたりしないでください。** 仕様に不足や矛盾を見つけたら、直さずに司令へ報告してください(設計判断は司令の担当)。

## 作業別の注意

- **仕様章の執筆**: 根拠ADRは司令が確定済みです。ADRに書かれていないことを仕様に書かないでください。EARS形式(「〜のとき、システムは〜すること」)と正例・負例、conformanceテストIDの予約まで行います。
  - `spec-write` スキルは締めに `spec-review` を実行すると定めていますが、**その手順だけは実行しないでください**。敵対的レビューは司令が `opus` で回します(このセッションでは最小モデルに落ちるため)。執筆が終わったらコミットして報告してください。
- **調査・実測**: 結論を出す前に、**測った生の数値をそのまま報告**してください。解釈は司令が行います。実装を書き換えて測った場合は、**必ず元に戻し、`git status` と `diff` で復元を確認**してから報告してください。
- **drift-check**: 矛盾を見つけても直さないでください。「どの文書のどこが、どの文書のどこと、どう矛盾するか」を列挙して司令へ返します。

## 報告

- 着手したら司令へ1通送ってください。宛先は `ListAgents` で `名前 [ref]` を確認して指定します(名前だけでは拒否されます)。司令のセッション名は渡されたプロンプトに書かれています。
- 完了したら、**何をしたか・テストの結果・判断に迷った点**を送ってください。
  - Redの完了報告には「どのテストが、どんな理由で落ちているか」を必ず含めてください。コンパイルエラーで落ちているのか、アサーション不一致で落ちているのかを区別して書きます。
- 送信できない、または司令が `ListAgents` に現れないときは、ユーザーがコピーできるようコードブロックで出力してください。
- 権限で拒否された操作を司令に代行させないでください。ユーザーへ確認してください。
