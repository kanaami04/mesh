# spec-review — 仕様章の敵対的レビュー

仕様の欠陥は実装後に見つかると手戻りが最大になるため、章の確定前に集中検査する。実績: 1章では2ラウンドで計26件(R1=18、R2=8)を実装前に検出した。

## 手順

### R1: 検出ラウンド(独立サブエージェント)

サブエージェントは **`opus` で起動する**(敵対的レビューの委譲規約=CLAUDE.md 協働スタイル・tddスキルのモデル表)。「対象章・根拠ADR(索引から辿る。superseded除く)・overview.mdの書き方ルール・設計監査文書」を読ませ、以下を指示する:

- **3つのペルソナで検査する**:
  1. **実装者** — この規則群だけでlexer/parser/型検査器を一意に実装できるか。未定義の入力、規則同士の衝突を具体的なコード例で示す。
  2. **敵対的ユーザー/AI** — 規則の裏をかく入力、エラーにならず静かに意味が変わるコード、他言語(TS/Go/Python)の手癖で書くと壊れる例。
  3. **整合性監査** — 根拠ADR・既存章・監査文書との矛盾、EARS規則/負例/テストID/エラーコードの対応漏れ。
- **最低検出ノルマ**: 章のEARS規則数の2割(切り上げ)以上。**「問題なし」での帰還は禁止**(LGTM禁止)。
- 深刻度を「要修正/要検討/軽微」で分類し、確信のない指摘には(未確信)を付ける。出力は発見リストのみ。

### 修正(メイン)

- 指摘を反映する。**設計判断を伴うもの(新しい決定・トレードオフ)は勝手に決めずユーザーに確認**し、確定したら `adr` スキルへ。
- 指摘が誤りだと判断した場合は握り潰さず「不採用+理由」を記録して検証ラウンドに渡す。

### R2: 検証ラウンド(同一エージェントをSendMessageで再開)

R1のコンテキストを保持した**同一エージェント**に指示する: ①R1全指摘の解消判定(解消/部分解消/未解消)、②**修正が新たに生んだ穴**の検出、③規則番号・テストID・エラーコードの整合。

### 収束条件

- 新規の**要修正がゼロ**になるまで「修正→検証」を繰り返す(上限3ラウンド。超えたら状況を報告してユーザーの判断を仰ぐ)。
- 完了時、PR本文に「検出→修正→検証」の要約(ラウンド別件数と主要指摘)を記載する。

## 章のセルフチェック(メインがR1と並行して実施。spec-kitの「要件の単体テスト」の考え方)

- [ ] 全EARS規則が「入力条件→コンパイラの挙動」の形で、そのままテストに落ちる
- [ ] 正例・負例がセット(負例の無い節が無い)/ 全負例にテストID予約
- [ ] エラーコード・規則番号の欠番・重複・参照ミスなし
- [ ] EBNFと診断規則の優先関係が明記されている
- [ ] 根拠ADRの全決定が章に現れている(決めたのに書いていない規則が無い)

## 役割分担

| スキル | 対象 |
|---|---|
| **spec-review**(このスキル) | 仕様章の新規執筆・大改訂(重い品質ゲート) |
| doc-review | md変更全般の軽量レビュー(仕様章の軽微な修正はこちらで足りる) |
| drift-check | フェーズ完了時の全量検査 |
