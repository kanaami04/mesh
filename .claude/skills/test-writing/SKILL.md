# test-writing — Meshコンパイラのテスト規約

役割分担: **tddスキル**=プロセス(Red→Green→Refactor)、**docs/testing-strategy.md**=戦略(4層・正負例セット)、**このスキル**=具体的な書き方。

## コマンド(このマシン固有)

cargoはPATH外にある。すべてのcargo実行は次の形:

```
export PATH="$HOME/.cargo/bin:$PATH" && cd /Users/kanayama/kanaami/language && cargo test
```

該当テストのみは `--test <ファイル名>`。Greenの成功条件には `cargo fmt --all --check` と `cargo clippy --all-targets -- -D warnings` を必ず含める。

## 配置と命名

- TDD対象のテストは `tests/<モジュール名>.rs`(統合テスト。例: `tests/lexer.rs`)。cargo既定の配置なので、ファイルを追加するだけで自動発見される(Cargo.tomlの編集は不要)。スナップショットは `tests/snapshots/` に生成される。
- fn名は英語snake_caseで「入力→期待」を表す(`empty_source_produces_no_tokens`)。
- 各テストに日本語docコメントで振る舞いを1文書く。**仕様の規則に対応するときは規則番号を書く**(例: `仕様1章L-6`)。
- **1テスト=1検証項目、assertは原則1つ**(2026-08-15ユーザー決定)。複数入力を検証したいときは関数を分ける。`expect`(Okである前提の確認)はassert数に数えない。パラメータ化テストcrate(rstest等)は導入しない——関数分割なら「テスト名=仕様文」の価値が保てる。
- 同一検証項目の複数入力は代表1入力に統合してよい。ただし**統合前に、元の各入力が検証していた境界が代表入力にも残るか確認する**(教訓: `_tmp`+`_1` を `_tmp1` に統合したら「`_` 直後が数字」の並びが消えた——これは別検証項目であり統合不可。初適用のimpl-reviewが重大として検出、2026-08-15)。
- **AAAパターン+マーカーコメント**(同決定): テスト本体を `// Arrange` `// Act` `// Assert` の3コメントで区切る。Arrangeが入力1行でも省略しない(省略ルールを作らないほうがAI生成が安定する)。スナップショットテストは対象外。入力は `let source = ...` に束縛してActで使う。

## 期待値の書き方

- **丸ごと明示**する: `assert_eq!(tokens, vec![Token { kind: TokenKind::Int, text: "42".to_string() }])`。`is_ok()` だけ等の曖昧検証は不可。
- `expect` のメッセージは日本語で「〜であること」(失敗時にそのまま仕様文として読める)。
- **例外(巨大入力)**: 期待値の丸ごと明示が非現実的な生成入力(64段ネスト等)に限り、形状検証(トークン数等)まで緩めてよい。理由をdocコメントに明記する(実例: nesting_depth_at_limit_is_accepted)。境界の検知力は対になる負例(65段=E0118)が担保する。
- **例外(負例の語彙表ループ)**: lexは最初のエラーで停止するため、負例の語彙表(誘導用予約語22語等)は1入力に併合できない。この場合に限り配列+forループで全語を検証してよい。失敗メッセージ(assert・panicとも)に**必ず語名を含める**こと(実例: all_guidance_reserved_words_report_e0104)。正例の語彙表は1入力にスペース区切りで並べて種類列を検証する(all_full_reserved_words方式)——ループにしない。

## TDDサイクル中の分担(実証済みの運用)

- **Redのスタブ規則**: テストのコンパイルに必要な型定義のみ追加してよい(enumバリアント・struct・シグネチャ。中身は `todo!()`)。ロジックは1行も書かない。「コンパイルエラーで落ちる」はRedではない——assertionまたは`todo!()`のpanicで落ちること。
- **Greenの最小主義**: テストに無い挙動を先取りしない。実例: 未対応文字は最小の `Err(LexError)`(黙殺スキップは暗黙の仕様決定になるので不可)、予約語は `"let"` 1個のif比較(一覧テーブル化はテストが増えてから)。
- **Refactorはメイン**: 2回出た走査パターンは部品化する(実例: `scan_while`=最長一致の共通部品)。リファクタ後に全テスト+fmt+clippyを再実行。

## スナップショット(insta)の併用

- **TDDサイクルの検証には使わない**(期待値明示のassertで回す)。サイクル群の完了後に**回帰の網**として追加する。
- 書き方: テストファイル末尾に `insta::assert_debug_snapshot!(対象式)`。スナップショットは `tests/snapshots/` に生成される。
- 初回生成: `INSTA_UPDATE=always cargo test --test <名前>`(PATH・cdは上記コマンド形)→ 生成された `.snap` を**必ず目視レビュー**(内容が仕様と一致するか)→ 通常実行で緑を確認 → `.snap` もコミットする。
- 意図しない差分が出たら「実装のバグ」か「仕様の意図的変更」かを判断し、後者のみ更新する。

## 負例テスト(エラーになるべきコード)

字句エラーのspan+E0105/E0116サイクル(2026-08-15)で実証した規約:

- 期待値は **`Err(LexError { code, span })` を丸ごと明示**する。`is_err()` やcodeだけの検証は不可(位置の劣化を検知できない)。
- **spanは違反箇所をピンポイント**で指す(実例: `1__0` は違反した `_` 1バイトの `1..2`)。「リテラル全体」を指す実装は、修正候補の提示(style-guide原則4)に必要な精度が出ないため不可。
- fn名にエラーコードを含める: `<入力の性質>_reports_e0105_with_span`。
- エラーコードは文字列でなく **`ErrorCode` enumのバリアント**で表す(タイポで存在しないコードを作れない)。
- 同一規則の負例なら複数ケースを同関数に入れてよい(`1__0` と `1_`)。

## conformance対応(仕様の負例IDとの1:1)

- 負例テストのdocコメントに**仕様の規則番号と負例ID**を書く(実例: `仕様1章L-9〔負例: underscore-edge〕`)。このIDが仕様→テストの対応表を兼ねる(専用の対応表ファイルは自作ランナー導入まで作らない)。
- 仕様の負例のうち**未実装機能に依存するケースは先取りしない**。docコメントに「`0x_FF` は16進実装のサイクルで追加」のように送り先を明記し、実装サイクル側で拾う。
- **IDの先行予約**(2026-08-15ユーザー承認): 仕様のテストIDは、対応する実装が未着手の場合に限り、仕様の対応表に「(○○サイクルで実装)」の注記つきで先行予約できる(実例: `comment-before-continuation`——2026-08-15に予約し、終端挿入サイクルで回収済み)。回収先を**roadmapの該当タスク行にも書いて二重追跡**にする。注記のない未実装IDは「仕様に書いたのにテストが無い状態」の違反であり、impl-review・drift-checkの検出対象。

## 変異解析(ミューテーションテスト)でテストの網を検査する

字句解析器の再レビュー(2026-08-18・ADR-0047・PR #31)で実証した検査手法。**テストが全部緑でも、網が粗いことはある。** 再レビューの開始時点でテストは142本あり全て緑だった。しかし実装をわざと壊すと次々とテストを素通りし、穴は最終的に7つを数えた。テストを159本まで増やして初めて、全変異が落ちるようになった。

変異解析(ミューテーションテスト)とは、実装をわざと壊してテストが落ちるかを見る手法。注入した壊し方を「変異」、変異に対してテストが落ちないことを「生存」と呼ぶ。生存は「その変異を検知するテストが無い」ことの証拠で、テストの**数**ではなく**検知力**を測れる。

### 変異の3類型

変異の型によって見つかる穴が違う。3類型すべてを回すこと(実例はすべて2026-08-18の字句解析器):

| 型 | 変え方 | 実例 |
|---|---|---|
| 削除・置換 | 条件を消す・一覧の項目を足し引きする・写像を取り違える(1箇所の機械的な変更) | `brackets.pop()` を `clear()` に替える/`is_continuation_token` の一覧に `RBrace` を足す/`(` と `[` を同一視 |
| 意味論の深さ | 参照の仕組み自体を替える | 「スタックの先頭だけ見る」を「末尾から探して同種が見つかればそこまで戻す」に替える(パーサでよくある回復ヒューリスティック) |
| 条件を広げる | ガードから限定条件を外す | 3文字目先読みのガード `matches!(kind, EqEq \| BangEq)` から種別条件を外す(結果: 2文字演算子全般の直後の `=` がE0116になる) |

- 削除・置換型は1ラウンド目で見つかった穴。後者2型は2ラウンド目で初めてメニューに加え、**テストを157本まで増やしてもなお生存した**。
- 後者2型の正体は「実装を弱くする」変化ではなく「**もっともらしい別実装**」への差し替え。実装者もレビュアーも書きそうなコードだから、将来の退行として現実に起きる。1ラウンド目のメニューに入っていなかったのはこのため。

### なぜ後者2型を忘れがちか

境界値のテストが「深さ1」に偏ると、正しい実装と別実装の区別がつかなくなる。

- 深さ1(スタックに要素が1個)では、「先頭だけ見る」と「末尾から探す」は同じ結果を返す。区別には**深さ2+種類の違う閉じ括弧**が要る。実例: `f([a\n)\n b\n]\n)\n` は先頭だけ実装でNewline 1個、深追い実装で4個になる(テスト `mismatched_close_paren_at_nested_depth_keeps_newlines_suppressed`)。
- 種別ガードも同じ理屈。`===`/`!==` だけを試すテストは、ガードの条件の有無を区別できない。**ガード内の種別以外**の入力が要る。実例: `a <== b` は `<=` と `=` の2トークンに割れ、E0116ではない(テスト `less_equal_followed_by_eq_splits_into_two_tokens`)。
- 教訓: 「釣り合わない入力を1組」だけでは足りない。深さを変え・種類を変えて、同じ規則の別の面を突く入力を揃える。

### 手順と安全規則

1変異ずつ「注入→実行→復元」で回す。cargoの実行形は「コマンド」節に従う。

1. `git status` がクリーンであることを確認する。
2. 変異を1つ注入する。
3. `cargo test` を実行し、落ちたか生存したかを記録する。
4. **必ず元に戻す。** `git checkout -- <対象ファイル>` で復元し、`git status` と `git diff` で汚れが残っていないことを確認してから次の変異へ進む。

- 復元忘れは壊れた実装をそのままコミットする事故になる。PR #31では毎回 `diff -q` でバイト一致まで確認した。
- 生存した変異には、殺すテストとの対応を記録する(どの変異がどのテストで落ちるか)。テスト統合の判断材料になる。
- 生存を塞ぐテストは**仕様から期待値を導いて**書く。変異後の実装に合わせて書くと、変異が基準にすり替わる。PR #31では変異ピンを順次追加し、テストは142→159、全変異が落ちる状態になった。

### いつ回すか

- **impl-reviewの観点A(仕様適合とテストの穴)のレビュアーへの指示に含める。** 2026-08-18の字句解析器再レビューがこの形の初例。レビュアーはモジュールが守るべき仕様規則(L-21・L-25)ごとに変異を注入して検査する。
- 全テスト緑でも変異が1つでも生存したら「テストの穴」として指摘する。処理はimpl-reviewの深刻度表(重大/改善/メモ)に従う。
- 毎サイクル回す必要はない。再レビューやフェーズ完了のように、テストの網に確信が欲しい節目で回す。
